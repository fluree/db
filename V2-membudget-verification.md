# V2 — R3-B Typed Memory-Budget Blind-Spot Verification (adversarial)

## 0. Charge, method, verdict

I am the adversarial VERIFIER; my job was to REFUTE the A1 §5 claim that the R3-B typed memory budget has a scan-path blind spot. Read-only checkout `<audit-checkout>` pinned at the audit tip `10e073fe9` (verified `git rev-parse HEAD` READ). Receipts are `path:line` in that checkout, labelled READ (observed), INFERRED (reasoned from READ facts), MEASURED (from lambda-audit's live CloudWatch forensics). No live queries, no writes to tracked files, no GitHub. Every attempt to find a second accounting path FAILED, so the three sub-claims survive; two are NARROWED from "unbounded" to "structurally bounded but GB-scale and unaccounted", which does not rescue the budget.

VERDICT IN ONE LINE: sub-claim (1) CONFIRMED, (2) CONFIRMED-NARROWED (bounded at O(concurrency≤32), not unbounded), (3) CONFIRMED; the blind spot is real, has a real historical OOM in it (the 071cd59f crawl), and a single wide/fact-parent crawl can put ~11 GB of entirely-unaccounted resident memory in front of a budget that `checkpoint()` never consults on this path.

## 1. Sub-claim (1) — the scan materialize path never `record_alloc`s its resident window: CONFIRMED

READ: `record_alloc` has exactly seven non-definition call sites, all on aggregating/joining operators — `hash_join.rs:676`, `group_aggregate.rs:853/891/977`, `fused_aggregate.rs:1336/2251/2303` — plus the `ExecutionContext::record_alloc` wrapper (`context.rs:759`) and the core primitive + its unit tests (`cancellation.rs`). A full-tree grep of `fluree-db-query/src`, `fluree-db-api/src`, `fluree-db-core/src` returns nothing else.

READ: `R2rmlScanOperator` (`operator.rs`) contains SIX cancellation polls — `check_cancelled()?` at `:955, :1158, :1400, :1484, :1534, :2616` — and ZERO `record_alloc` and ZERO `checkpoint()`. So the plain crawl/materialize path is cancellation-aware but memory-blind: it can be aborted by an external timeout / RSS-watchdog signal, but it never contributes a byte to `allocated_bytes()` and never compares its residency against the budget.

READ: the resident window is real and named. `next_batch` (`operator.rs:2599-2704`) materializes one window per `advance_one_window` call (`:2665`), emits `ctx.batch_size` rows (default 1000, `context.rs:369`), and spills the remainder of the window into `self.pending` (`:2618-2623`). The window is `DEFAULT_MATERIALIZE_WINDOW_ROWS = 512*1024` (`operator.rs:209`, env `FLUREE_R2RML_MATERIALIZE_WINDOW_ROWS`). The in-tree comment quantifies the fat-binding cost: "a full-table materialize of a 6M-row scan is ~14 GB" → ~2.3 KB/materialized row for a wide crawl (`operator.rs:201-206` READ). So `self.pending` alone holds up to ~512K rows ≈ **1.19 GB** for a wide row, unaccounted.

INFERRED (bound, the honest NARROW): the window is NOT unbounded — `self.pending` peaks at ~one 512K-row window because the pull loop drains `pending` (1000 rows/emit) before `advance_one_window` materializes the next (`operator.rs:2618` gate precedes `:2665`). The scan-replay cache #12 is capped at 512K rows (`collect_scan_capped(fresh, materialize_window_rows(), …)`, overflow streams uncached — READ), the per-operator parent cache #13 ≤512K, and the query-scoped parent memo #11 ≤2×512K = ~1M rows via `parent_memo_total_cap_rows()` (`operator.rs:131-137`) enforced by `try_insert`'s `total_rows.saturating_add(rows) > total_cap` refusal (`operator.rs:108-115` READ). So each individual structure is capped — but the caps are GB-scale, a query holds MANY of them (one window + one replay + one parent cache per scan operator, plus the shared memo), and NONE is recorded. "Bounded" here means "bounded well above the budget", not "small".

INFERRED (the cap has a hole): the ≤512K memo cap bounds only RETAINED entries; `build_parent_lookup(parent_tm, join_cols, parent_batches)` (`operator.rs:1288`) builds the FULL lookup for the current batch regardless of size, and only THEN does `try_insert` refuse to retain a >window lookup (`operator.rs:1298-1322`). So a fact-as-parent (the q015 hazard the comment names) transiently builds a full-fact-sized map — e.g. 36M entries ≈ several GB — resident during the batch's materialize, unaccounted and NOT bounded by the 512K cap. This is strictly worse than the A1 window claim.

## 2. Sub-claim (2) — O(concurrency) in-flight file buffers invisible: CONFIRMED, NARROWED to bounded-O(32)

READ: the fan-out is `futures::stream::iter(tasks).map(spawn read_task).buffer_unordered(concurrency)` (`r2rml.rs:2138-2191`), `concurrency = iceberg_scan_concurrency(tasks.len())`. The default is `available_parallelism.min(num_files).clamp(1,32)` (`r2rml.rs:80-83` READ) — so the A1 "1..32 clamp" is exact. The `FLUREE_ICEBERG_SCAN_CONCURRENCY` override is `n.min(num_files.max(1))` — UNCAPPED past 32 (`r2rml.rs:73-78` READ), but the task fixes "default switches", so ≤32 holds.

INFERRED: `buffer_unordered(concurrency)` IS backpressure — at most `concurrency` file reads are in flight — so the buffer is structurally BOUNDED at O(concurrency), refuting a literal "unbounded" reading. But each in-flight `read_task` returns the WHOLE file's decoded `Vec<ColumnBatch>` at once (`r2rml.rs:2186` flattens `Result<Vec<ColumnBatch>>` — the file is fully decoded before any batch leaves the task), so per-file residency = (raw bytes held) + (decoded Arrow for the whole file).

READ (the 64MB figure and its neighbours): `MAX_SPARSE_BUFFER_SIZE = 64MB` (`send_parquet.rs:99`) is the threshold above which the reader switches from a sparse projected-column buffer (files ≤64MB) to `RangeBackedChunkReader` on-demand ranges (files >64MB, `read_task_large_file` `:641`). So the A1 "~64MB each" is the sparse-buffer ceiling for the common ≤64MB file. The crawl-specific worst case is larger: `admit_whole_file` reads the ENTIRE file when `cheap` (≤`WHOLE_FILE_MAX_BYTES`=32MB) OR `broad` (projection ≥`WHOLE_FILE_MIN_SHARE_PCT`=50% of bytes) (`send_parquet.rs:150-158` READ), capped at `LARGE_FILE_ADMIT_MAX_BYTES`=256MB (`:117`). A wildcard `?p ?o` crawl projects ALL columns → broad → whole-file admission up to 256MB per file. So the buffer ceiling is 32×64MB≈2 GB (typical) up to 32×256MB≈8 GB (broad crawl over large files), plus the decoded Arrow.

READ (no second accounting path — refutation FAILED): the only `budget_bytes()` in `fluree-db-iceberg` is the DISK-cache size limit (`send_parquet.rs:500/652/884`), not the query RAM budget; there is no `record_alloc` / `mem_used` / `allocated_bytes` / `MemoryBudget` anywhere below the seam, and no ColumnBatch heap-size accounting. So the entire columnar decode + in-flight file buffers are invisible to the R3-B budget. CONFIRMED.

## 3. Sub-claim (3) — `set_memory_limit` has no non-test callers, so no per-query division: CONFIRMED

READ: `set_memory_limit` (`cancellation.rs:177`) is called only from its own two unit tests (`cancellation.rs:269/278`) and the two R3-B hermetics `r3b_hash_join_build_budget_aborts_typed` (`hash_join.rs:1118`) and `r3b_group_aggregate_budget_aborts_typed` (`group_aggregate.rs:1235`) — both `#[tokio::test]`, both pinning the "1-byte ceiling" pattern (I read the enclosing test bodies to confirm). No production caller exists.

READ: therefore `checkpoint()` (`context.rs:780-796`) always takes the `unwrap_or_else(query_memory_budget_bytes)` branch — the process-wide `OnceLock` budget = 78% of the detected container / 8 GiB fallback / 0 disables (`context.rs:35-50`). INFERRED: N concurrent queries each compare their OWN query-scoped `allocated_bytes()` counter against the SAME full budget; two queries each accounting 5 GB both read "under 8 GB" and neither trips, while the node is at 10 GB. So even on the ACCOUNTED join/aggregate paths the budget over-admits by the concurrency factor. On the unaccounted scan path (§1/§2) division is moot — there is no counter to divide.

INFERRED headline: a modest wide crawl carries ~1.2 GB (window) + ~1.2 GB (replay) + ~2 GB (file buffers) ≈ **~4.4 GB** unaccounted; add one fact-as-parent lookup build and it reaches **~11 GB**, exceeding both the 8 GiB budget and the 10 GiB Lambda ceiling — with `record_alloc` seeing zero of it. Multiply by N concurrent queries (no division, §3): N×4.4 GB OOMs a 10 GiB node at N≈2. The one live backstop is solo's RSS watchdog; because the crawl path DOES poll `check_cancelled` between windows (`operator.rs:2616`), the watchdog CAN convert a slow crawl to a 507 — but it cannot stop a single un-checkpointed spike inside one `spawn_blocking` Arrow decode or one rayon materialize window (neither polls mid-operation, INFERRED).

## 6. `BINDING_EST_BYTES` = 64 vs a true 88-byte `Binding`

READ: the constant is `pub const BINDING_EST_BYTES: usize = 64;` (`context.rs:55`); the companion `GROUP_EST_BYTES = 128` (`context.rs:57`). The true stack size is documented IN TREE: `binding.rs:14-17` states that boxing `RelValue` keeps `size_of::<Binding>()` at **88 bytes** (an unboxed payload "would push the enum from 88 to 104 bytes"). So the estimate under-counts the STACK footprint by (88−64)/88 = **27%** before any heap.

INFERRED (the heap gap, worst for R2RML): the variants an Iceberg query actually produces own heap allocations neither 64 nor 88 counts — `Binding::Iri(Arc<str>)` (graph-source IRIs, `binding.rs:98`), `IriMatch{iri, ledger_alias: Arc<str>}` (`binding.rs:82-89`), `Lit{val: FlakeValue(String), …}`. A typical IRI binding is ~88 stack + ~50-70 heap (Arc<str> + 16 B ArcInner) ≈ **~140 B**, so `record_alloc` counts ~46% of the true footprint — an under-count of ~2.2×, worst exactly on the IRI-heavy rows the virtual path emits.

INFERRED (relationship to sub-claim 1): MECHANICALLY INDEPENDENT — sub-claim (1) is absent accounting (the scan path calls `record_alloc` zero times); the 64-vs-88 defect is under-accounting WHERE `record_alloc` IS called (the fold/join). But they COMPOUND the same failure: on the instrumented paths the budget's real trip point is ~1.3× (stack) to ~2.2× (heap IRIs) above the intended 8 GiB, so `hash_join.rs:676`'s `batch.len()*ncols*64` lets the 36M-interior build (the 818s specimen's driver) overshoot to ~10-12 GB real before `checkpoint()` fires — weakening R3-B on the very path the forensic OOMs lived. `GROUP_EST_BYTES=128/group` is likewise a flat estimate that a Collect/GROUP_CONCAT accumulator blows past.

## 7. Fix sites (no code changes made)

INFERRED, minimal, in priority order. (A) Scan-window accounting: replace `check_cancelled()?` with `checkpoint()?` at `operator.rs:2616` (the pull-loop top) and add `ctx.record_alloc(window_rows * num_cols * BINDING_EST_BYTES)` where `advance_one_window` materializes the window (`operator.rs:1371+` / the `self.pending` fill), plus `ctx.record_alloc(lookup.len() * PARENT_ENTRY_EST_BYTES)` at the `build_parent_lookup` result (`operator.rs:1288`) so the fact-as-parent build is visible BEFORE retention is decided — this closes sub-claim (1) and the §1 cap-hole. (B) In-flight buffer accounting: record per-file admitted bytes at the fan-out (`r2rml.rs:2138-2191`, e.g. `record_alloc(task.data_file.file_size_in_bytes)` on admission, release on batch flush) — closes sub-claim (2); note this needs a `release`/decrement primitive the current monotonic `AtomicUsize` counter lacks (`cancellation.rs`). (C) Per-query division: pin `cancellation.set_memory_limit(query_memory_budget_bytes() / active_query_count)` at handle attach (`runner.rs:828-829`) — but `active_query_count` is not tracked in-engine, so the authoritative source is the server that spawns the watchdog and holds the handle (`fluree-db-server/src/query_control.rs`); this is the deeper of the three. (D) Under-count: bump `BINDING_EST_BYTES` 64→88 (`context.rs:55`) at minimum, or make it heap-aware for IRI-bearing bindings — cheap and independently worthwhile.
