# Implementation-phase adversarial diff reviews (audit PRs)

House rule: every audit PR gets one adversarial diff review before it leaves draft. Reviewer plays the V1/finding author trying to defeat the change. Verdict per finding: BLOCKING / NONBLOCKING / PASS. Receipts are `file:line` at the reviewed commit.

## R-1520 — PR-SAFE-MOR: fail-closed merge-on-read delete guard (F-AUD-1), commit 771f6e88b, base main, DRAFT

Scope: 9 files, +599/−6. New module `fluree-db-iceberg/src/mor_guard.rs` (summary + manifest-list checks, per-table warn-once override); 3 snapshot summary accessors; `IcebergError::MergeOnReadDeletes`; guard wired into BOTH scan planners (`planner.rs`, `send_planner.rs`) and the preview UX (`iceberg_catalog.rs`); docs + env switch. I reviewed as the V1 author trying to slip a MoR snapshot past it. VERDICT: SHIP #1520 on main (the guard is complete on main); FIX-FIRST the perf-line cherry-pick (finding F1). One V1 amendment.

### F1 [BLOCKING for the perf-line cherry-pick; NONBLOCKING for #1520-on-main] — the scan-files cache bypasses the guard, and the disk tier survives a pre→post-guard upgrade

READ: the guard lives INSIDE `SendScanPlanner::plan_scan` / `ScanPlanner::plan_scan` (send_planner.rs:84-106, planner.rs:202-224). But `scan_table_inner` reaches scan tasks by FOUR arms (r2rml.rs:1830-1916): (1) filtered → `plan_scan` [GUARDED]; (2) in-memory scan-files cache hit `cache.get_scan_files` → rebuilds tasks from `cached.data_files` [NO plan_scan]; (3) DISK scan-files cache hit `catalog_disk_cache().get_scan_files` → rebuilds from `disk.data_files` [NO plan_scan]; (4) miss → `plan_scan` [GUARDED]. Arms 2 and 3 reconstruct the scan WITHOUT invoking the guard, and `CachedScanFiles` (cache.rs:24-29: `data_files, estimated_row_count, files_selected, files_pruned`) carries NO delete signal — unlike the COUNT path's count-stats cache, which correctly stores `has_delete_manifests` (r2rml.rs:1193).

INFERRED (why arm 2 is safe but arm 3 is not): both caches are populated ONLY in the miss arm, AFTER the guarded `plan_scan` (r2rml.rs:1918-1934) — so a post-guard binary, whose `plan_scan` REFUSES a MoR snapshot, never writes a MoR plan to EITHER cache. The in-memory cache (arm 2) is process-scoped, so within a post-guard process it can never hold a MoR plan → safe-by-construction (and it is the ONLY scan-files cache on main — `disk_catalog_cache.rs` is branch-only, confirmed `git ls-tree origin/main`). The DISK cache (arm 3) is cross-process AND cross-binary, keyed by the immutable `metadata_location`, 512MB under `/tmp`: a PRE-guard binary (today's deployed engine) that scans a MoR table writes its delete-stripped `data_files` to disk; a later POST-guard binary gets a disk hit and rebuilds the scan, silently returning deleted rows — the exact F-AUD-1 failure, past the guard.

INFERRED (severity, honest bounds): on Lambda the deployed risk is ~nil — `/tmp` is per-container-ephemeral, so a new deployment means fresh containers with an empty disk cache (pre-guard entries never coexist with the post-guard binary). The real window is a LONG-LIVED server (or shared/persistent `/tmp`/EFS) upgraded in place, where a pre-guard-cached MoR plan is served until the entry ages out. Because the cherry-pick targets the general engine (BYO/server, not only solo-Lambda), a correctness guard shipping with a known bypass should not read as "complete." FIX (cheap, mirrors the count-stats cache): add `has_delete_manifests` to `CachedScanFiles` and to the disk `CachedScanFiles`, and on a cache hit (arms 2+3) call `ensure_no_delete_manifests(usize::from(has_delete), …)` before rebuilding tasks — a stale pre-guard disk entry lacking the field decodes to `false`, so ALSO version/namespace the disk-cache key (or bump its schema) so pre-guard entries are not read post-upgrade. This is the highest-value branch-drift finding; #1520-on-main does not have arm 3 so it ships clean.

### F2 [NONBLOCKING] — the COUNT path is guarded only TRANSITIVELY, and lacks an end-to-end refusal test

READ: the PR adds NO guard call to the production COUNT path (`stats.rs` change is a TEST only; r2rml.rs is not in the diff). Instead `table_row_count_inner` (r2rml.rs:1134-1210) relies on the pre-existing `sound_manifest_row_count` (r2rml.rs:2222-2228: `if has_delete_manifests { return None }`) declining the manifest shortcut, after which the fused operator streams its fallback → a full scan → the guarded `plan_scan`. INFERRED: sound, because `sound_manifest_row_count` returns `Some` ONLY when `has_delete_manifests==false`, and the count-stats cache preserves `has_delete_manifests` across a hit (r2rml.rs:1193) so a cached count still declines. But it is INDIRECT: the only tests are (a) the guard-function unit tests and (b) `stats_path_refuses_delete_manifests_unless_overridden`, which asserts the PATTERN (a consumer calling `ensure_no_delete_manifests` refuses) — NOT that `table_row_count`→`None`→fallback→refuse end-to-end. ## R-1521 — PR-SAFE-MEM: close the memory-budget blind spot on the non-aggregate scan path (F-AUD-3), HEAD 1441e0038, base perf/audit-tier012, DRAFT

Scope: 3 files, +355/−35 in fluree-db-query. context.rs — `BINDING_EST_BYTES` 64→`size_of::<Binding>()` (=88) + a compile-time `const _` floor assert; new `query_budget_share_div()`/`per_query_memory_ceiling()` (site C division). runner.rs — attach-time per-query ceiling pin, gated `div>1 && memory_limit().is_none()`. operator.rs — site A1 (materialized-window `record_alloc`+`checkpoint` in `advance_one_window`), site A2 (per-batch `record_alloc`+`checkpoint` in `build_parent_lookup`), the pull-loop poll upgraded `check_cancelled()`→`checkpoint()`, kill switch `FLUREE_SCAN_MEM_ACCOUNTING` (default on), 5 hermetics. I reviewed as the V2 author trying to slip an OOM past it. VERDICT: SHIP — no blocking findings; three bounded, documented, conservative-direction residuals + two nits. DIVISION CALL: ACCEPTABLE-RESIDUAL for this PR.

### F1 [NONBLOCKING] — site A1 charges the right shape but a stack-only magnitude, and records POST-materialize

READ: site A1 (operator.rs:1457-1475) records `produced.len() * num_cols * BINDING_EST_BYTES` = binding-count × est — the correct quantity shape (V2's "materialized window"), and `checkpoint()` right after. Two honest caveats, both the PR documents. (i) MAGNITUDE: `BINDING_EST_BYTES` is now the 88-byte STACK size, but an IRI-bearing crawl row (`Binding::Iri(Arc<str>)` — the 071cd59f shape) owns ~50-70B of heap the stack size never sees, so the window is counted at ~44% of true residency; at `div=1` (ceiling = 78% of container) a WINDOW-dominated IRI crawl can reach ~1.7× container before the recorded counter crosses 78% → the typed abort may not beat the OOM for that sub-class. This is the SAME conservative floor the existing fold/join `record_alloc`s use (they under-count heap too), so the PR does not introduce it — it EXTENDS the scheme and IMPROVES it (64→88); a heap-aware estimate is the documented follow-up and should apply to ALL sites, not just scan. (ii) PLACEMENT: A1 is POST-grow — it records the window that was JUST materialized, then checkpoints before the loop pulls the NEXT window (operator.rs:1465 record is after the materialize call, before `emit_produced_window`). So the abort prevents the next window but not the current one; overshoot is bounded to one `materialize_window_rows` window (~1-2GB wide-crawl, capped, and capped tighter under a LIMIT). Acceptable (unbounded accumulation → bounded one-window overshoot is the win). RECOMMEND: a scan-path heap-aware/2× per-binding estimate so the abort reliably precedes the OOM for IRI crawls; optionally a pre-grow check (project the next window against the budget before materializing).

### F2 [NONBLOCKING] — site A2 accounts the derived MAP but not the upstream `collect_stream` parent-scan spike; Send-safe

READ: site A2 (operator.rs:2547-2560) records `batch.num_rows * PARENT_ENTRY_EST_BYTES` (200 B, a sound estimate for a `(Vec<String> key, RdfTerm)` entry) PER BATCH and checkpoints BEFORE inserting the batch's rows — pre-grow at batch granularity, and the parent-scan batches are small (~parquet decode batch), so a single batch cannot overshoot meaningfully. Good. GAP: `build_parent_lookup` consumes `parent_batches`, which `collect_stream` (operator.rs:1473-1490) has ALREADY fully drained from the parent scan — and `collect_stream` polls only `ctx.check_cancelled()?`, never `record_alloc`/`checkpoint`. So for the fact-as-parent hazard (36M-row parent), the parent scan's COLUMNAR batches are materialized unaccounted (~hundreds of MB to ~1GB) BEFORE A2 sees the first entry. A2 catches the DOMINANT term (the ~7GB fat map — columnar input is ~8× smaller than the materialized map), and A2's first-batch checkpoint aborts immediately if the collect already pushed the counter over — but the collect's own bytes are invisible, so a bounded (~parent-columnar-sized) spike precedes the abort. RECOMMEND: account `collect_stream`'s batches (a `record_alloc(batch bytes)` + `checkpoint` in its drain loop, mirroring A2). SEND-SAFETY (the repo's async-recursion trap): `build_parent_lookup` is a SYNC fn and `collect_stream`/`advance_one_window` already hold `ctx`; the PR adds only sync `record_alloc`/`checkpoint` calls and NO new async recursion, so no non-Send future is introduced on the r2rml paths. Clean.

### F3 [DESIGN CALL — ACCEPTABLE-RESIDUAL] — static divisor default 1 is the sound minimal form; dynamic is genuinely deferrable

READ: runner.rs:829-840 pins `set_memory_limit(per_query_memory_ceiling(full, div))` only when `div > 1 AND cancellation.memory_limit().is_none()`. Judgement: the static divisor is the CORRECT minimal division, and the deferral of a dynamic (live-concurrency) divisor is justified on TWO grounds, one of which the PR under-sells. (a) The stated reason (nested policy/reasoning/sub-query re-entry would miscount a live in-engine counter) is real — but note the PR's own `memory_limit().is_none()` guard ALREADY neutralizes it: a nested re-entry inherits the parent's set ceiling and skips, so nested calls do not re-divide. (b) The DEEPER, unstated reason that actually blocks a cheap dynamic form: a live-count divisor has a mid-flight ORDERING hazard — query A enters alone (count=1 → pins the FULL budget), query B arrives (count=2 → pins half), but A is already mid-flight at full and cannot be re-pinned, so A still overcommits. Sound dynamic division needs mid-flight re-pin (hard) or a max-concurrency bound — and a max-concurrency bound IS the static divisor. So there is NO cheap safe dynamic form shippable in this PR; the server-boundary deferral (a reserved-concurrency / semaphore ceiling in query_control.rs) is the right home. RESIDUAL (the open gap, documented): `div=1` default = zero concurrent-overcommit protection out of the box — F-AUD-3 sub-claim 3 stays open unless the operator sets `FLUREE_QUERY_BUDGET_SHARE_DIV = reserved concurrency`; solo's RSS watchdog remains the only default backstop (exactly V2's conclusion). ACCEPTABLE for this PR PROVIDED the recommendations ladder carries "set the divisor on the Lambda to its reserved concurrency" as the completing DEPLOYMENT action (not a code fix) and the gap is flagged open (the PR's doc comments do). Default-1 is the correct default (a non-1 default would silently throttle single queries).

### F4 [PASS] — the hermetics pin the regressions (by inspection; physical revert not run — Rust build cost)

READ: `r3b_scan_window_budget_aborts_typed` builds a REAL `R2rmlScanOperator` over a `?s ?p ?o` wildcard crawl (the 071cd59f shape) with a mock provider, pins a 1-byte ceiling, and asserts `advance_one_window` returns `MemoryBudgetExceeded` — it drives the PRODUCTION `advance_one_window`, so on the parent commit (no site-A1 `record_alloc`/`checkpoint`) that call returns `Ok`, the `expect_err` panics, and the test FAILS: it pins A1. `r3b_parent_build_budget_aborts_typed` drives the production `build_parent_lookup` (which on the parent does not even take `ctx` → won't compile there; with A2 it aborts on the first batch): pins A2. `binding_est_bytes_is_at_least_binding_stack_size` asserts `BINDING_EST_BYTES == 88` → fails on the parent's `64`. The two ceiling tests exercise the new pure division fns. All 5 pin their change; the two OOM-regression tests structurally require the new checkpoints to pass. (I did not physically revert-and-run — a full Rust rebuild — but the A1/A2 tests' dependence on the site checkpoints is unambiguous from the diff.)

### F5 [PASS, with a nit] — `FLUREE_SCAN_MEM_ACCOUNTING` off is OBSERVABLY byte-identical, but the pull-loop upgrade is not switch-gated

READ: with the switch off, sites A1/A2 are skipped (no `record_alloc`), so the scan path contributes 0 to the counter. BUT the pull-loop poll `check_cancelled()`→`checkpoint()` (operator.rs:2668-2677) is UNCONDITIONAL — off does not revert it. `checkpoint()` = `check_cancelled()` + a budget compare; with the scan recording nothing, `used` reflects only upstream operators, and every upstream recorder (hash_join / group_aggregate / fused) ALREADY self-checkpoints, so the scan's added compare is redundant and the query aborts at the same point it would pre-PR → observably byte-identical. So the switch's "clean revert to the prior behavior" claim holds for OUTCOMES but is technically imprecise (the pull-loop now budget-checks unconditionally). RECOMMEND: gate the pull-loop poll (`if scan_mem_accounting_enabled() { checkpoint() } else { check_cancelled() }`) for a literal clean revert, or soften the doc to "byte-identical outcomes; upstream-recorded budget is enforced here too, which upstream operators already enforce."

### F6 [NONBLOCKING nit] — fmt-only churn inflates the diff

READ: several hunks are pure `cargo fmt` reflows unrelated to the change — `star_free` (operator.rs:594), `star_required_preds` (operator.rs:863), and three test-body reformats (f16 gate, ref_template_shortcut). Harmless, but they enlarge the review surface of a correctness-sensitive PR; ideally isolate them in a separate fmt commit.

### Verdict + division-call answer

SHIP. The PR closes V2 sub-claim 1 (scan-window accounting, site A1) and the fact-as-parent hazard (site A2) ON BY DEFAULT, fixes the 64→88 under-count with a compile-time floor guard, and ships per-query division as a sound static opt-in. Every residual (A1 heap under-count + one-window post-grow overshoot; A2's unaccounted `collect_stream` input; `div=1` default) is BOUNDED, DOCUMENTED, and in the conservative (over-count / fail-late-not-wrong) direction — none is a correctness regression, and all match the pre-existing R3-B accounting philosophy. AMENDMENT TO V2/F-AUD-3: V2 named four fix sites; this PR lands A1 + the ceiling-division (C) + the 64→88 (D). ## R-CACHE-ARM — fix for the R-1520 scan-files-cache bypass, commit 9c6739c3b, perf/audit-tier012 (7 files, +134)

Reviewed as the R-1520 finder trying to re-open the bypass. VERDICT: CLOSED. The fix implements exactly the R-1520 remedy (delete-flag on the cache entry + re-check on both hit arms + version bump) and adds a re-refuse-on-override-flip property that needs no cache invalidation. No blocking findings; two minor observations.

Attack 1 (bypass closed / other consumers) — CLOSED. READ: the only production `get_scan_files` consumers are the two hit arms (r2rml.rs:1847 in-memory, :1877 disk), and each is immediately followed by `guard_cached_scan_files(...has_delete_manifests, loc)?` (:1850, :1884) — the disk arm's guard fires BEFORE the promote-to-in-memory `put_scan_files`. Every `CachedScanFiles`/`PersistedScanFiles` construction site (r2rml.rs:1928 write, disk_catalog_cache.rs:410/423 round-trip) sets the flag — Rust's all-fields-required construction makes an omission a compile error, so no path can produce an unstamped entry. The shared helper means the two arms can't drift.

Attack 2 (stamp false yet deletes present — the belt case) — CLOSED. READ: the stamp is `summary_indicates_deletes(snapshot) || delete_manifests > 0` (planner.rs:232, send_planner.rs:108), computed from the SAME two signals and the SAME `delete_manifests` count (`parse_manifest_list_with_deletes(…,true).filter(is_deletes).count()`) the guard itself refuses on. The stamp is precisely as strong as the guard — it inherits only the guard's own pre-existing, V1-accepted parse-drift limit (both summary omits AND `is_deletes()` misreads content → false), introducing NO new false-negative.

Attack 3 (version gate on READ, v2=miss-not-error) — CLOSED. READ: `CACHE_FORMAT_VERSION 2→3`; the versioned envelope is checked before the payload is trusted and "a mismatch (or any deserialize failure) is a miss, never an error." The new test `pre_guard_v2_scanfiles_entry_is_a_miss_recomputed` writes a v3 entry (flag=true), downgrades `format_version` to 2 on disk, and asserts `get_scan_files` is `None` (a miss → recomputed through the guard). Observation (non-blocking): the version is GLOBAL, so the bump also invalidates v2 metadata/count-stats/pointer payloads — a broader one-time recompute than scanfiles alone, but safe (over-invalidation only recomputes).

Attack 4 ("flag only true under override" + override-off refuses) — CONFIRMED. READ: the stamp line is reached only AFTER both `ensure_no_summary_deletes` and `ensure_no_delete_manifests` — which return `Err` (guard active + deletes) before it — so a plan with `has_delete_manifests=true` is only PRODUCED, hence only cacheable, under the override. `guard_cached_scan_files` reads `mor_deletes_allowed()` FRESH and calls `ensure_no_delete_manifests(usize::from(flag), loc, allow_mor)`, so a flagged entry with the override now OFF is REFUSED (typed `MergeOnReadDeletes`, naming the switch — test `cached_scan_files_guard_refuses_delete_bearing_entry`), not skipped. The re-check at hit time means turning the override off re-closes the guard without invalidating the cache — a clean property.

Attack 5 (recompute cost per-snapshot not per-query) — CONFIRMED. READ: the cache is keyed by the immutable `metadata_location`, so a v2→miss recompute runs once per snapshot (the first query touching it after the upgrade writes v3); subsequent queries hit the v3 entry. Per-snapshot, not per-query.

Minor (non-blocking): no test drives the actual DISK-arm code path (r2rml.rs:1877-1884) end-to-end with a flagged v3 entry + override off — the helper is unit-tested in isolation and the v2-miss is tested, but the disk-arm wiring (1884) itself is exercised only by inspection. The wiring is a one-liner identical to the tested in-memory arm; low risk.

VERDICT: CLOSED. R-1520 F1 is resolved on the perf line — both hit arms are guarded, the stamp mirrors the guard's two-signal belt exactly, pre-guard disk entries are excluded by the version bump, and the override state is re-evaluated at hit time. The MoR guard is now complete on the perf line as it already was on main.

### 1. GATE SOUNDNESS (top) — the shared-oracle blind spot is the load-bearing fact

`verify_twin` (materialize.rs:753) builds its SOURCE oracle by calling `materialize_graph` (materialize.rs:769) — the SAME enumerator (`emit_batch`, graph.rs:311) the twin was built from via `drive_virtual_import` (materialize.rs:618). So the gate diffs `enumerator-output` vs `enumerator-output-round-tripped-through-ingest+index+query-back`. It validates the ADAPTER→sink→commit→index→query-back path; it CANNOT catch an enumerator logic bug (wrong FK join, wrong datatype coercion, wrong template) because that bug is present identically on both sides and they AGREE. This is exactly design §9 TOP RISK, acknowledged; the only independent enumerator oracles in-repo are the golden suite (graph.rs tests) and `materializer_driver_matches_engine_wildcard` (12-triple airline mock, diffs enumerator vs the query engine's `?s ?p ?o` — genuinely independent at the orchestration level, but shallow and shares the per-term helpers). The blessed native-sf01 full-triple diff — the real enumerator oracle — is DEFERRED (lead-run). Per corruption class, given the gate compares value-canonicalized N-Triples SETS:

- **(a) count-neutral drop on an UNSAMPLED subject** — CAUGHT(Full) / ESCAPES(Quick, the default). A dropped `rdf:type` triple always lowers the class count (count is over the SET; a "compensating duplicate" adds nothing to a set — the dropped+duplicated attack is structurally void), so type-triple drops are CAUGHT even in Quick (count:CLASS check, materialize.rs:793). A dropped NON-type triple on a subject outside the lexicographically-first-3 of its class escapes the Quick sample and is only caught by `--verify full`. Systematic drops (every subject loses `name`) surface in the sample by construction → CAUGHT.
- **(b) value corruption surviving numeric canonicalization** — CANNOT survive. `normalize_numeric_lexical` (materialize.rs:950) is STRICTLY trailing-fractional-zero stripping (`"5.00"→"5"`, `"5.10"→"5.1"`); scientific notation bails unchanged; the datatype IRI is preserved in the output (materialize.rs:944). It can NEVER equate distinct values ("5"≠"50", "5.1"≠"5.01"); leading-zero forms (`"0.5"` vs `".5"`) are treated as DISTINCT — i.e. the only failure mode is OVER-strictness (a spurious diff = fail-closed/safe), never a false match. So corrupted values are CAUGHT wherever compared; the only escape is the (a) unsampled-Quick gap. NONBLOCKING nit: doubles/floats re-rendered in E-notation by the twin will false-FAIL the diff (safe direction) — the LIVE diff will need real value-space float compare, which the code comment (materialize.rs:923) already flags.
- **(c) predicate/lang/datatype swaps** — CAUGHT (sampled/Full). `sample_checks` (materialize.rs:1008) compares the full triple set per subject; a swapped predicate/lang/datatype yields a set difference. Systematic → in every sample → CAUGHT. Unsampled single-row swap → Full only.
- **(d) FK to a wrong-but-existing parent** — CAUGHT from the CHILD side (sampled/Full): the sample compares the child's full OUTGOING node doc, which includes its FK edge (`<child> <pred> <parentB>`), so a redirected edge diffs. Every class is sampled, so a child class's FK edges are covered. BUT an enumerator FK-resolution bug is invisible (shared oracle, above). Incoming-ref coverage of a sampled subject is not asserted (only outgoing), but is covered transitively when the child is sampled.

Sampling is DETERMINISTIC (BTreeSet lexicographic first-`SAMPLE_SUBJECTS_PER_CLASS=3`, materialize.rs:734/1018), NOT seeded/random — full coverage of systematic bugs by construction, ZERO tail coverage for truly-random per-row corruption. Coverage gap: the Quick default has NO negative test — `verify_twin_fails_on_corrupted_twin` injects a count-INCREASING extra instance and runs `VerifyMode::Full`; the always-on stratified sample is exercised only by the PASSING case. ### 3. THE STAMP — rides the final commit; partial builds detectable, PASS

`drive_virtual_import` (materialize.rs:601-664) uses a one-chunk lookahead: `pending` always holds the most-recently-closed group; each newly-closed group flushes the PREVIOUS as a non-final chunk (`stamp=None`), and the last held group is emitted last with `Some(&stamp)` (materialize.rs:663).
