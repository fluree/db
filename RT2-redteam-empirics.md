## Attack 1 — the 8–91× fused-escape claim: CORRECTED (qualitative HOLDS, magnitude overstated ~16×)

RECOMPUTED (denominators sound): q014 reads all 7,670 FACT_ORDER files (`iceberg.parquet_read.n=7670`, whole table) → 180,000-row denominator is the full scanned table; q027 reads all 7,670 FACT_WEB_EVENT files → 1,000,000-row denominator sound. Walls match: q014 hot 119 ms (median [122,116,119]), q027 hot 197 ms. So 180000/0.119 = 1,512,605 rows/s and 1000000/0.197 = 5,076,142 rows/s are arithmetically correct AS whole-process rates.

RECOMPUTED (the basis error — the core finding): the 56k ceiling is explicitly PER-CORE — master F-AUD-15 "53–57k rows/s/core", C1 envelope "wall ≈ rows/(56k×cores)". C2 §6 divides a WHOLE-PROCESS fused rate by this PER-CORE ceiling: 1,512,605/56,000 = 27.0× (stated) and 5,076,142/56,000 = 90.6×≈91× (stated). On a consistent basis (÷16 cores, or equivalently ceiling×16 = 896k whole-process): q014 hot = 94,538 rows/s/core = 1.69×; q027 hot = 317,259/core = 5.67×; q014 WARM = 27,641/core = 0.49× (BELOW the ceiling — it is I/O-bound). C2's own mechanism claim ("fused throughput is bounded by scan/decode, not binding materialization") CONFIRMS the divisor: scan/decode runs 16-way parallel (`buffer_unordered(min(16,files).clamp(1,32))=16`), so its whole-process rate MUST be divided by the parallel core count to compare against a per-core ceiling. So "8–91×" → ~1.7–5.7× (average, hot) on a consistent basis.

INFERRED (the qualitative claim SURVIVES, via the numbers C2 should have led with): (a) MARGINAL throughput removes the fixed-cost confound — (1,000,000−180,000) rows / (0.197−0.119)s = 10,512,821 rows/s whole-process = 657,051 rows/s/core = 11.7× the per-core ceiling; the fused path's per-row cost genuinely beats materialization by ~12×/core. (b) The CLEAN apples-to-apples datum is C2 §5's own "decisive pair": q014 warm 407 ms vs q038 warm 58,935 ms, both COUNT-shaped, both whole-process walls = 144.8× (row-normalized 407ms/180k vs 58935ms/427.5k = 2.26 vs 137.9 µs/row = 61×). So the reframe (fused does no per-row RDF binding, escapes the ceiling) is TRUE and robust; the "8–91×" is just the wrong way to size it. RECOMMENDATION: replace "8–91× above the ceiling" with "~12× marginal per-core throughput" or the 145×/61× q014-vs-q038 wall/per-row ratio; either is defensible, "91×" is not.

CORRECTED (coupled number): C2 §6 line 119 lists native q014 = 293 ms / 614,334 rows/s (11×), but the delivered native oracle `native-full-10e073fe9.jsonl` shows q014 = 199 ms (all_walls [214,197,196,199,199]) = 904,523 rows/s. 293 ms appears nowhere in native q014's reps. The conclusion "fused virtual BEATS native hot" SURVIVES (virtual 119 ms < native 199 ms), but the native rate is understated by 47% (614k vs 904k), inflating the virtual-vs-native margin from 1.67× to 2.46×. Fix the table cell (and master §3 "native comparator 614k/s").
