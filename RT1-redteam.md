## TARGET 1 — the DataFusion Step-1 recommendation (B1 §4/§5c/Appendix D)

### T1-b — "Step-1 absorbs the decline chain": REFRAMED (the load-bearing finding)

READ: the fused fast path is entered by `detect_fused_r2rml_aggregate` (operator_tree.rs:2474); on a `None` from detect the tree falls through to `build_operator_tree_inner(&fallback_query, …, false, …)` (operator_tree.rs:2485) — the generic row-materialization pipeline with fused fast paths DISABLED. So a query detect rejects never reaches any fused operator. READ: for a query detect ACCEPTS, the 5 decline gates live at OPEN, in `resolve_at_open` (fused_aggregate.rs:1470), which has ~12 `return Ok(None)` points (1475/1511/1527/1531/1535/1542/1548/1552/1555/1566/1601/1605); on any decline the operator sets `use_fallback=true` and streams `self.fallback` (fused_aggregate.rs:1088-1090, 1345-1347) — again the generic pipeline. MEASURED(the round-3 engine analysis §1): the canonical OOM query declines all five gates (join-path FILTER, non-linear order_chain, cross-dim keys, cross-table expr, interior fact) inside `resolve_join_at_open`.

INFERRED (the refutation): B1 §5c defines Step-1 as DataFusion "behind the exact admission gate `fused_aggregate.rs` already uses … for the shapes it currently fuses," yet claims it "immediately absorbs the decline chain (5-gate OOM query, mixed keys, interior fact, SUM(expr), spill)." Those are contradictory. The admission gate is `resolve_at_open`; a query that fails it streams the generic fallback, NOT DataFusion. To make DF handle the 5-gate query, DF must be invoked WHERE the fallback is today AND admit shapes `resolve_at_open` declines — i.e. it must REPLACE the decline logic with a wider relational lowering. That is B1's own Step-2 ("widen the gate"), which is exactly where the semantic-soundness surface (T1-a) and the real effort sit. So the recommendation's headline benefit — closing the F-fix decline tail / fixing the killer families — belongs to Step-2, not Step-1.

INFERRED (the deeper cut): for the shapes Step-1 DOES target (resolve-admits: single-table + FK-linear-join grouped aggregates), the fused fold ALREADY folds columnar with no per-row RDF materialization (A1 §2 step 8) — so those shapes never pay the 56k-rows/s ceiling today. Therefore BOTH of Step-1's advertised wins (absorb the decline chain; remove the 56k ceiling) accrue to Step-2. Step-1's honest, narrower value is: replace the hand-rolled fold's bespoke arithmetic/spill with a maintained engine FOR ALREADY-FUSED SHAPES — a maintenance/robustness win, not a capability or throughput win. B1 should re-attribute: Step-1 = maintenance swap (low value, low risk); Step-2 = the actual killer-family fix (high value, and where all the T1-a/T1-d soundness cost is).

### T1-a — semantic soundness at the lowering boundary: HOLDS (B1 under-weights the arithmetic domain)

READ: the fused fold does EXACT decimal arithmetic — `bigdecimal::{BigDecimal,BigInt}` (fused_aggregate.rs:44-45) with an `i128` fixed-point fast path (`ExactDecimal{val:i128,scale}`, :90-98) that on overflow "escalates to the exact BigDecimal pipeline rather than wrap around" (:94) and keeps NULL-drop distinct from overflow-escalate (:176-178). So today's SUM/AVG is arbitrary-precision, no-rounding, no-overflow. INFERRED: "construct RDF terms only on output" does NOT rescue this, because the AGGREGATE ARITHMETIC runs in the engine's numeric domain BEFORE output — DataFusion sums in fixed Decimal128/Decimal256 (38/76 digits) or f64, which can overflow or lose precision where the current path escalates to BigDecimal. This is a VALUE-CHANGING divergence (wrong sum), not a term-rendering one. B1 §5c/Trade-offs frames the correctness surface as "nulls, duplicates, datatype-correct term construction" and calls it "bounded, well-mapped" — it MISSES that the arithmetic domain itself changes. MEASURED (memory: bakeoff/corpus): the corpus already encodes this sensitivity — SUM(SHIP_COST) is excluded as "f64-nondeterministic" while SUM(csatScore xsd:integer) is kept as "exact i128 → deterministic"; a DF swap to Decimal128 SUM would require re-blessing every decimal-SUM oracle and risks silent divergence on high-scale/large-magnitude sums. Net: DF converts B1's "unbounded per-shape decline tail" into a "bounded per-shape arithmetic-parity tail" — genuinely better, but it is still a per-shape validation cost, i.e. the same class of cost B1 says DF eliminates, and the exact-decimal fidelity is a real regression risk B1 does not price.

## TARGET 2 — the materialization strategy shape (C3, C4, master §4)

### T2-a — direct-S3 build + head-publish OUTSIDE the transactor: REFUTED (C3 is right and under-sold it)

I attacked expecting an unserialized head-publish race. READ (the protocol that refutes it): the DynamoDB nameservice publish path is CAS-guarded end-to-end — ledger/head CREATE is conditional `attribute_not_exists(pk)` (mod.rs:671,1103,1150) inside atomic `TransactWriteItems` (743); the commit-head ADVANCE is `publish_commit` conditioned `attribute_exists(#pk) AND #ct < :t` (mod.rs:1229) — a MONOTONIC-t compare-and-swap; index advance is `#it < :t` (1966); graph-source publish is exact-CAS `#id = :exp_id AND #t = :exp_t` (1789). INFERRED: therefore an out-of-band builder and any concurrent writer cannot cause a lost update or a head rollback — the stale/lower-t writer fails `ConditionalCheckFailedException` (handled at 487-496). For the TWIN pattern (fresh ledger → build → alias-repoint), the initial publish is a conditional create + monotonic advance, S3 objects are content-addressed (idempotent; orphans harmless per C3 §3), and crash-safety is S3-first-then-atomic-head. So C3 §3's "builder → import → head publish, zero engine changes, assembly job" (labeled INFERRED) is CORRECT and was under-sold — it never cited the CAS protocol that makes it safe. NARROWED residual: safety requires publishing via the SAME nameservice `publish_commit`/`publish_index` path (a hand-rolled DynamoDB put bypassing the conditions would be unsafe — but nothing proposes that); and the CAS ENFORCES the twin-and-repoint discipline (you cannot in-place-overwrite an advanced twin: `publish_commit(t=1)` fails `#ct < :t` once deltas reached t=5 — a correct refusal, not a bug). The real residual gaps are the ones C3 already named (hard-delete retraction, >40GB initial load, worker persistence), NOT concurrency.

### T2-b — "the pack protocol is already incremental" → usable for twin sync?: NARROWED / REFRAMED

READ: `pack.rs:65-157` is a want/have commit BFS + index-artifact set-diff — the git-fetch-shaped clone/pull REPLICATION path (docs/cli/server-integration.md:8). INFERRED: this ships store-to-store deltas between two FLUREE stores (a built twin → a replica), computed by the receiver's have-set over CIDs it already holds — it works on live stores (content-addressed). But it is ORTHOGONAL to the Iceberg→twin FRESHNESS problem: refreshing a twin from Iceberg is NOT a Fluree-store pull; it is #1422's snapshot-window walk + the (unbuilt) removed-file retract lane (C3 §7, §10). So master §4's headline "Sync: cheaper than expected. The pack protocol is ALREADY incremental" conflates two problems — pack-incremental solves twin REPLICATION (real, unexposed), while Iceberg→twin DELTA is still #1422 with a hard-delete blind spot. C3's body separates them correctly ("Iceberg-side increments via #1422 … Deletes remain the hard part"); the master's juxtaposition oversells. Minor cost C3 omits: the index-artifact set-diff must enumerate CIDs reachable from the want index root — a tree walk over the (large at SF20) index structure, not free.

### T2-c — SF20 arithmetic error bars: NARROWED (error is directionally SAFE; one favorable point unflagged)

READ/MEASURED(C3 §5): 22.4 B/triple flat from SF0.1 (35.24M triples / 751 MiB), split commit 4.5 / index 9.0 / dicts 8.7. INFERRED: dicts do NOT scale linearly — a star schema's dimension values (categories, names, cities) saturate; only high-cardinality columns (keys, timestamps) grow ~linearly, so dict B/triple DECREASES at 200× → the 8.7-flat term OVER-estimates the ~57GB dict share, making the 147GB total a conservative HIGH (real likely ~115-130GB). Index (9.0) is roughly flat-to-slightly-super (leaflets ~linear dominate; internal-node/tree-depth overhead is sublinear). So the error bar is ~±20-30% in the SAFE direction, NOT ±3× — C3 is honest (it shows a 22.3-40.2 anchor range and labels the scale INFERRED). UNFLAGGED favorable point: dict sublinearity means more per-table packs clear the 40GB door than the linear estimate implies (the 120M-row fact at "~27GB" is likely ~22GB — more margin). HOLDS on the softest number: build time. C3's "~90 min at 1.30M flakes/s" is MEASURED on LDBC SNB (a different shape) and C3 flags it INFERRED/unmeasured — I add: the rate DEGRADES at scale (deeper index, larger dict lookups per insert → build plausibly 2-3× the estimate), and the single-machine memory ceiling for a 7B-flake single-ledger build is unaddressed (auto memory-budget has OOM'd a machine before — fluree-cli-demo-gotchas). Build parallelism: C3 correct — in-process only; horizontal scale needs per-table ledgers (a different data model) or is future work (create.rs).

### T2-d — twin + alias-repoint atomicity vs in-flight queries: NARROWED (DB layer safe; solo layer unverified)

READ: the DB engine resolves the dataset→ledger binding ONCE per query, attaching it to the ExecutionContext at runner attach (`with_dataset`, runner.rs:834) — not re-resolved per operator/batch. INFERRED: so a mid-query alias-repoint cannot switch engines under an in-flight query at the DB layer (the per-query resolution is the protection, the same shape as the per-query Iceberg snapshot pin V2 verified). HOLDS as unverified: whether solo's dataset-row ledger-pointer SWAP is itself atomic (a single conditional DynamoDB update → a starting query sees old-XOR-new, never neither/half) is a SOLO-side question out of the db audit's scope and is NOT verified anywhere in C3/C4; master §4 presents "alias-repoint" as a pattern, not a verified-atomic mechanism. Flag it for a solo-side check before the pattern ships.

### T2-e — freshness semantics users actually get: HOLDS (a product cost the decision framing omits)

READ(C3 §6): a twin's t advances per SYNC BATCH; time-travel resolves to sync-batch boundaries; the retract→upsert pair leaves a visible intermediate t; post-#1508 a fact whose whole lifetime fits one indexing window is invisible to index-served time-travel. INFERRED: so materializing a dataset TRADES freshness for speed — the twin is stale by up to the sync interval (minutes-to-hours), whereas the live-virtual path is near-live (pinned Iceberg snapshot, pointer-cache TTL ≤300s). Master §4's "materialization is a per-table/per-family lever" is correct but omits that the lever COSTS freshness; that is a product decision (a BI rollup family may tolerate hours-stale; an audit-trail claim may not), and "time travel over your warehouse" is weaker on a twin than the pitch implies (C3 §6 says as much for the pitch; the master's decision framing should foreground it).
