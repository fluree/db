## 0. Framing — the residual families, the correctness lemma, and the three axes

THE RESIDUAL TIMEOUT FAMILIES (what remains over the wall at the deployed pin `10e073fe9`, verbatim from READ(C1 §2/§3), given short labels used throughout): **R1** = big single-FACT grouped rollups ≥~60M rows, CPU-materialize-bound at `wall ≈ rows/(56k×6)` (36M→107s, 60M→178s, 120M→357s, 200M→590s, all > the 180s cap); **R2** = 2-FACT join rollups (120M⋈36M), memory-bound → now a bounded TYPED FAIL (507/OOM), not a success; **R3** = unfiltered VALUES/FILTER-IN scans (lowering to a set-valued scan filter never emitted — the `Expression::In` pruning backend exists, nothing feeds it); **R4** = predicate-less whole-dataset COUNT (q056, 69,046 files — un-fused COUNT decodes every object row); **R5** = get_data_model on a HYBRID/non-empty-shell dataset (C2's manifest path is gated on `ledger.t()==0`, so a virtual-that-is-also-committed ledger takes the federated scan); **R6** = any sweep-bound shape at SF20 COLD (fetch-floor × cold catalog × half concurrency × NO cross-container cache — per-container `/tmp` is cold on every cold container).

THE SNAPSHOT-KEYED CORRECTNESS LEMMA (the load-bearing enabler for most of the design space). READ(A1 §3): the content-addressed cache layers (parsed metadata, scan-file selections, footers, count-stats, and the disk-catalog copies of each) "can never go stale because their key IS the immutable snapshot's `metadata_location`," and the per-query snapshot pin (caches #8/#10) "guarantees every scan in one query reads ONE Iceberg snapshot even if the table commits mid-query." INFERRED (the generalization every option below rides): ANY artifact that is a pure function of one Iceberg snapshot S — a cached final result, a stats/NDV sidecar, a rollup cube, a decoded dim table, a deterministic sample, a bloom index — is EXACTLY-CORRECT when served to a query pinned to S, byte-for-byte indistinguishable from live computation, because it is content-addressed by S (equivalently by S's immutable `metadata_location`). The ONLY staleness axis such an artifact adds is "which snapshot does a NEW query pin?" — and that is the ALREADY-DEPLOYED bounded-staleness question governed by the existing pointer TTLs (READ(A1 §3): disk pointer 300s, in-mem loadTable 60s, per-query pin 0s); adding the artifact changes nothing about it. CONSEQUENCE: every acceleration option here EXCEPT #6 (a synced native twin, which advances on its OWN sync clock, not the source snapshot) inherits the deployed consistency model for free and adds no new correctness surface — with ONE shared caveat: an artifact BUILT on today's scan/stats path inherits the V1 MoR-delete over-count (READ(V1): position/equality delete files are silently ignored, so a scan/COUNT over a merge-on-read table returns deleted rows and over-counts), so any sidecar/cube/result BUILD must gate on the same fail-closed delete guard V1 recommends (refuse when `total-delete-files/position/equality > 0`) or it durably snapshots a wrong answer. Second, minor: some shipped levers are "rows_only, not byte-identical" (READ(A2): F17 budget-met skip, F9 CURIE) — a RESULT cache (#1) must normalize ordering / key on set-equality, not raw bytes.

THREE ORTHOGONAL AXES (a complete strategy draws from each — this is a decomposition, not a ranking). **DEMAND-ELIMINATION** — answer without the full compute (result cache #1, sidecar cubes #3b, partial-result reuse #10, approximate #8, and the product-tier P.1 "MCP surfaces stats so the agent stops firing 39 rollups" from READ(the strategy slate P.1)): cheapest per unlock, but a REUSE/ESTIMATE lever — it does not make a first, novel, exact compute finish. **CAPACITY-ADDITION** — compute the full thing faster or bigger (the DataFusion reference axis, shared warm tier #2, scatter-gather MPP #4, per-source SQL pushdown #5, per-table promotion #6): raises the wall itself. **ENVELOPE** — change WHEN the answer may arrive (async/continuation #7): neither faster nor cheaper, converts a 504 into a late result. INFERRED: the deployed failure set needs all three — e.g. R1 wants a cube (demand) OR DataFusion/MPP (capacity), first-populated via async (envelope); no single option closes the tail alone.

## Reference axis — DataFusion Step-1 (the B1 recommendation; assessed-against, NOT re-enumerated here)

READ(B1 §5c, App-D3; 00-MASTER F-AUD-16): lower the RELATIONAL subplan (scan+filter+join+group-by) to an in-process Apache DataFusion plan over OUR already-pruned `ScanPlan{tasks}` (READ(B1 D3): `planner.rs:130` already emits the exact handoff surface — selected files + projection + residual + field-id schema — and `decode_batches_arrow` already yields Arrow `RecordBatch`es), constructing RDF terms only on the small OUTPUT rows — inverting the cost model from "materialize every INPUT row" (the measured flat 56k rows/s/core ceiling, READ(C1 §1d)) to "materialize every OUTPUT row," inheriting upstream vectorized hash-aggregate + external-sort spill + cost-based join reorder. Family reach: DIRECTLY R1 (vectorized aggregate → seconds not minutes for ≤~tens-of-M output-feeding rows) and R2 (spill + semi-join → the OOM join COMPLETES instead of typed-failing). Does NOT by itself fix R6 (same IO layer → same fetch floor), R4's 69k-file fan-out (fetch, not decode), R3 (needs the IN-set lowering regardless), or the EXTREME tail (a 550M-row UNFILTERED rollup still decodes every row — seconds-to-tens-of-s, not O(1)). Coupled cost: an arrow 54→58/59 major bump (READ(B1 D1): the DELTA_BINARY_PACKED `skip_records` panic is fixed in arrow 58.2.0+, and DF pins arrow ~58/59, so do the bump and DF adoption as ONE coordinated move; blast radius confined to the `io/` module, ~25 typed downcasts). This is the EXECUTION-ENGINE axis; each option below closes with its relation to it (complementary / orthogonal / partially-superseded).

## 1. Snapshot-id-keyed RESULT cache (query-hash × snapshot → serialized result)

Mechanism: after a query resolves its pinned snapshot(s), hash the normalized query text + the pinned `metadata_location`(s) + the policy/identity context into a key; on hit, return the stored result body; on miss, compute live and store. Backing store = DynamoDB (small results) with S3 spill (large), both already in the solo stack. Precedent is standard: READ+WEB(https://www.thelakehousepath.com/p/understanding-query-caching-in-databricks) Databricks SQL warehouses reuse cached query results on subsequent identical runs and expose `from_result_cache` telemetry; the lakehouse novelty here is keying on the immutable Iceberg snapshot so the cache never needs invalidation.
Rescues: the REPEAT-DEMAND slice of EVERY family — R1/R2/R3/R4/R5/R6 all collapse to a metadata lookup on the SECOND identical (query, snapshot). Strongest for R5 (get_data_model is highly repeated and small) and for canned BI-dashboard / canned-agent-probe traffic on a stable snapshot.
Does NOT rescue: the FIRST/cold compute of anything — a 590s R1 rollup cannot even be computed to POPULATE the cache within 180s (needs #7 async or #4 MPP to produce it once); and the deployed agent pattern of "~39 DISTINCT rollups in one turn" (READ(the strategy slate exec-summary)) has near-ZERO within-turn hit because each rollup's full-query-hash differs (that overlap is #10's target, not this one). So this is a DEMAND lever, not a capacity lever.
Primitives vs net-new: RIDES solo's DynamoDB + S3 (the STATUS_TABLE / RECORD_TYPE pattern, READ(C4)). NET-NEW = a canonical query-hash, a result-serialization + size policy (READ(C1 §1a): buffered invoke 6MB / stream ~20MB caps bound what is inline-cacheable; bigger spills to S3), and the key composition.
Consistency: snapshot-keyed = EXACTLY-correct per the §0 lemma; resolve the current snapshot via the existing pointer path FIRST, then look up (snapshot, hash). Inherits the V1 MoR caveat only if the cached body was computed on the delete-ignoring path (gate the BUILD).
Size: **S–M**. Dominated by the key/serialization/spill plumbing, not by any engine change.
Failure modes: cross-identity LEAK if policy/authz is not in the key (a policy-filtered result served to a different identity is a data breach — the key MUST include the resolved policy context); hash collisions (use a strong hash); rows_only nondeterminism (normalize ordering / set-equality); a poisoned entry from a pre-guard MoR-wrong compute (gate build on the V1 delete guard); result-body size (S3 spill).
DataFusion relation: ORTHOGONAL — caches the OUTPUT regardless of how it was produced; DF is complementary (it makes the first compute cheap enough to populate the cache synchronously, shrinking the set that needs #7 to populate).

## 2. Shared WARM tier for catalog + footers + hot ranges (cross-container read-through)

Mechanism: a cross-container read-through cache below the existing per-container `/tmp` `DiskArtifactCache`/`disk_catalog_cache` (READ(A1 §3, caches #14/#15)), holding the catalog metadata + scan-file lists + loadTable pointers + Parquet footers + hot data-file ranges, so a COLD container skips the cross-region cold S3 re-read. Two concrete substrates: EFS-for-Lambda (shared POSIX mount) or S3 Express One Zone as a read-through in front of S3 Standard (READ(B1 §2e): AWS documents Express — single-digit-ms, ~9 GB/s — as a caching layer for Standard).
Rescues: **R6** directly — it is the architectural answer to "per-container `/tmp` is cold on every cold container; ALL shipped caching wins are warm-container-only and evaporate cold" (READ(C1 §3.6, A1 §)). Partially trims the COLD first-ask of every family by removing `T_catalog` + repeated footer/range fetches.
Does NOT rescue: R1 (materialize-bound — moves zero of the 56k-rows/s term), R2 (memory-bound), R3 (lowering-bound), or R4's row-DECODE (helps its fetch floor, not the per-row decode). This is a FETCH-floor lever only.
Primitives vs net-new: NET-NEW infra + wiring — C4 states plainly there is "NO shared cache tier" today and warns "don't build anything that assumes a second query benefits from the first's warmth unless same-container" (READ(C4, C4 solo-pipeline facts §4)). The CAS disk-cache CODE exists; making it cross-container (EFS mount in CFN, or an Express bucket + read-through) is the new surface.
Consistency: content-addressed by `metadata_location`/digest = EXACTLY-correct, identical to the local disk caches (§0 lemma); the pointer (which snapshot) keeps its TTL. A bigger, shared version of the existing `/tmp` CAS — same correctness. First cold container writes through; eviction by the tier.
Size: **M** (infra + read-through + eviction + single-flight to avoid a cold-stampede first-fill). WEB(https://lumigo.io/blog/unlocking-more-serverless-use-cases-with-efs-and-lambda/): EFS mounts in a few hundred ms and adds <20ms to cold start, and OS-page-cache means only the FIRST read of a file pays full latency — good for the repeatedly-read catalog/footers; BUT for frequently-changing or random ranges "S3 can win," so EFS suits the catalog/footer tier better than the random hot-range tier (measure per the strategy slate T3.3 first step).
Failure modes: EFS latency worse than a same-region S3 GET for random ranges (measure first); Express per-request cost; a shared tier is a shared poisoning/failure domain (mitigated by content-addressing); cross-tenant scan-file lists must be keyed by tenant `metadata_location`; the 300s pointer-TTL staleness window is inherited (READ(A1 §3)).
DataFusion relation: COMPLEMENTARY — DF still needs bytes fetched; a warm tier feeds its scan faster. Stacks with B1 §5b#3 async-prefetch (both fetch-layer).

## 3. ACCELERATION SIDECARS (per-snapshot auxiliary artifacts, built WITHOUT full native materialization)

Umbrella mechanism: for each snapshot S, build a SMALL derived artifact that answers a family of queries in O(artifact) instead of O(rows), stored snapshot-keyed. Four variants, sharing one builder and one correctness model.
**3a — Stats/NDV sidecar.** Per-snapshot table stats: row counts, per-column min/max/null-fraction, NDV, datatype distributions. Rescues **R5 on ANY dataset shape** (serves get_data_model from the sidecar, generalizing C2/T1.2 PAST the `t()==0` empty-shell gate — READ(the strategy slate T1.2)) and **R4** (whole-dataset COUNT = Σ record_count over the sidecar, instant). Feeds the PLANNER (selectivity → cost-based join order, semi-join decisions) which indirectly de-risks R2. Cheap: the Iceberg manifest already carries `record_count` + column bounds (READ(A1 §4)); NDV comes from Puffin Theta sketches IF the writer emitted them, else one amortized scan. WEB(https://iceberg.apache.org/puffin-spec/ , https://www.dremio.com/blog/puffins-and-icebergs-additional-stats-for-apache-iceberg-tables/): Puffin stores Theta-sketch NDV + blob stats; Theta sketches are single-pass, orders-of-magnitude faster, and INCREMENTALLY MERGEABLE (compute for new files, merge with existing — a cheap per-snapshot refresh, rides a #1422-style added-files window).
**3b — Pre-aggregated rollup cubes.** Precompute `GROUP BY <dim attr>` COUNT/SUM/AVG results per snapshot for the dominant families A/B/C. Rescues **R1 AT ANY SCALE** — a 550M-row rollup becomes a small cube lookup, INDEPENDENT of the 56k×6 wall. This is the standout: a native twin (strategy b) STILL full-scans a 550M-row unfiltered GROUP BY (READ(C3 §; 00-MASTER §4): "an unfiltered 550M-row GROUP BY is slow natively too; the rollup family's real cure is aggregate pushdown OR precomputed cubes"), so the cube is the materialization answer for the rollup family that the native-twin is NOT.
**3c — Value-index / bloom sidecars.** Per-file bloom filters / value indexes for equality + IN-set. Rescues **R3** (bloom prunes the equality the current min/max can't — READ(B1 §3a): bloom is the canonical fix; complements the parked IN-lowering) and hardens point-lookups. Parquet/Iceberg writers can emit bloom natively; the sidecar is needed only when the source didn't.
**3d — Denormalized wide-table / pre-joined sidecar.** Precompute the fact⋈dim star as one flat columnar artifact per snapshot. Rescues **R2** — the 2-FACT join collapses to a single-table scan (no HashJoin build → no 8-10 GB memory blowup, READ(C1 §3.2)); serves ARBITRARY queries over the join, not just pre-chosen aggregates (its distinction from 3b). Larger artifact (full join cardinality) but eliminates the memory-bound class.
Family net: 3a→R4+R5(+planner-help for R2); 3b→R1; 3c→R3; 3d→R2. Between them the sidecar family covers R1/R2/R3/R4/R5; and because sidecars are SMALL and warm-tier-cacheable (#2), a cold container reads a tiny cube instead of sweeping 69k files, so sidecars+#2 together largely dissolve **R6** for cube-covered shapes.
Who builds them: the solo self-reinvoke materialize-COORDINATOR pattern (READ(C4): coordinator Lambda → per-ledger SQS FIFO, batching + self-reinvoke near 900s, job-rows) is the natural builder — build on register + refresh on snapshot-advance (poll), OR build-on-MISS (first query of shape X on snapshot S triggers an async build, answered once via #7, cached after). Incremental refresh rides #1422's snapshot-window machinery (added-files only) and Theta-merge (3a).
Consistency: snapshot-keyed = EXACTLY-correct (§0 lemma). MoR caveat: a cube/stat built on the delete-ignoring scan over-counts → MUST gate the build on the V1 delete guard. Refresh lag = the pointer-TTL question, unchanged.
Size: **L overall** — 3a is S–M (manifest already holds most; NDV the exception), 3c is M, 3b and 3d are the L parts (a build+refresh coordinator + a rewrite/planner hook to recognize "answerable from cube" + artifact storage). WEB(https://aws.amazon.com/blogs/big-data/accelerate-query-performance-with-apache-iceberg-statistics-on-the-aws-glue-data-catalog/) confirms the pattern is industry-standard (Glue accelerates Iceberg queries via exactly these stats).
Failure modes: cube-MATCH false positives = serving a cube for a query it does not actually answer = WRONG (the match logic is a NEW soundness surface of the SAME risk class B1 §4 warns about for the hand-rolled fused-aggregate admission gate — this is the option's central hazard); false negatives fall to live (safe); the BUILD itself hits the 56k/MoR/OOM walls (building a 550M-row cube is a 590s job → needs #4 MPP or the async coordinator to build once); cube EXPLOSION (which GROUP-BYs to precompute needs telemetry → converges with #6); storage cost.
DataFusion relation: 3a/3c COMPLEMENTARY (feed DF's planner + pruning); 3b PARTIALLY-SUPERSEDED-BY-yet-COMPLEMENTARY-TO DF — DF makes live rollups fast enough that the cube's value drops for ≤~tens-of-M rows, but for 550M-row unfiltered rollups even DF decodes every row (seconds-to-tens-of-s) whereas the cube is O(1), so cubes still own the extreme tail + zero-latency dashboards; 3d COMPLEMENTARY (DF still benefits from not joining).

## 4. Scatter-gather MPP (K parallel Lambdas each scan a file subset + partial-aggregate; coordinator merges)

Mechanism: the coordinator pins ONE snapshot, shards the resolved scan-file list into K subsets, fan-out-invokes K worker Lambdas (each materializes/aggregates its shard), and merges the partials. Horizontal scale PAST the hard 6-vCPU single-Lambda ceiling (READ(C1 §1a): 10240MB = AWS max, no more RAM/cores buyable). Precedent: READ(B1 §2c) Starling (SIGMOD'20) + Lambada; WEB(https://anakli.inf.ethz.ch/papers/off-the-shelf-serverless_CIDR24.pdf , https://arxiv.org/html/2501.07771v1) the CIDR'24 off-the-shelf-serverless and 2025 empirical-evaluation lines confirm the shape is live SOTA.
Rescues: **R1** (K× the 56k×6 throughput → 550M/(56k×6×K): K=10→~59s, K=30→~20s), **R4** (69k-file COUNT is embarrassingly parallel), **R6** (K× fetch parallelism directly attacks the fetch floor), and **R2** with more work (partition the join by key across workers — a distributed hash join with S3 shuffle). The general CAPACITY-adder — it buys the "more cores" escape the strategy slate said a single Lambda cannot (READ(the strategy slate exec-summary)).
Does NOT rescue: **R3** (MPP scans the full VALUES set faster but the O(N·K) correlated match is still a missing-lowering rewrite issue — combine with #3c/IN-lowering); R5 is better served by 3a/T1.2 (metadata, not scan).
Primitives vs net-new: RIDES solo's async-invoke + SQS-FIFO + coordinator-self-reinvoke (READ(C4): the materialize coordinator is exactly this scaffolding) and the query Lambda AS the worker. NET-NEW and HEAVY = a scan-file SHARDER, a fan-out invoker, a partial-aggregate MERGE protocol, S3-shuffle for joins (Starling "doublewrite"), and straggler mitigation.
Consistency: the coordinator passes the pinned `metadata_location` + shard list to every worker → all workers read the SAME snapshot → EXACTLY-correct, the per-query pin cleanly GENERALIZED to a per-distributed-query pin (§0 lemma). This also lets workers SKIP the catalog (read only S3 data), which is essential (below).
Size: **XL** — a distributed execution engine (fan-out, shuffle, merge, stragglers, partial-failure, cost control). READ(B1 §2c): heavy, solo-owned, strategic-not-near-term.
Failure modes: catalog-429 STORM (K cold containers collectively DDoS the catalog — the PR-8 semaphore is PER-CONTAINER, READ(A2 PR-8); MUST pass the pre-resolved pinned location so workers never hit the catalog); per-worker cold cache (each worker cold → the warm tier #2 becomes load-bearing here); S3-shuffle cost+latency (WEB(https://arxiv.org/html/2501.07771v1): naive S3 shuffle is far slower than cluster shuffle — multiple write/read round-trips, and TB-scale needs THOUSANDS of requests; ephemeral-storage/aggregation tricks needed); straggler tail gates the merge; K× Lambda-second cost; coordinator SPOF (self-reinvoke helps).
DataFusion relation: COMPLEMENTARY — each MPP worker runs DataFusion LOCALLY (DF = the per-worker engine; MPP = the cross-worker layer). DF+MPP is precisely the modern serverless-analytics shape; they compose (DF makes each shard fast, MPP adds shards).

## 5. Per-source SQL pushdown fast path (Snowflake-managed segment ONLY)

Mechanism: when the source IS a Snowflake-managed Iceberg table (Polaris catalog + a Snowflake warehouse behind it), translate the relational subplan to SQL and push it to Snowflake — predicate/projection/aggregate/join/full-passthrough (READ(B1 §2d): the Trino Snowflake-connector + Starburst full-query-passthrough precedent) — receive a small result, build RDF terms on that.
Rescues (for the Snowflake segment ONLY): R1/R2/R3/R4 — Snowflake computes the rollup/join/COUNT/IN at warehouse scale, returns a tiny result; R5 via INFORMATION_SCHEMA. Essentially the WHOLE tail, for that one segment.
Does NOT rescue: ANYTHING on the BYO-IAM raw-S3 segment — READ(B1 §2d, App-C): "DOA for BYO raw-parquet with no engine behind it; there is nothing to push SQL to." This is a per-source fast path, NOT an architecture, and it re-introduces the warehouse cost/latency/dependency the "query in place without a warehouse" value-prop rejects.
Primitives vs net-new: NET-NEW = SPARQL→SQL (or DataFusion-plan→SQL unparser) + a Snowflake SQL execution/auth path + result mapping. The catalog AUTH exists; SQL execution is new.
Consistency: the ONE option where snapshot-pin correctness is NOT automatic — execution moves to an engine with its OWN snapshot view, so the pushed SQL MUST explicitly pin the same snapshot (Snowflake time-travel / snapshot-id) or it reads Snowflake's current, which may differ from the Fluree-pinned snapshot. A genuine consistency SEAM to close by construction.
Size: **M–L** (SQL lowering + connection + auth + result mapping; bounded by reusing a plan-unparser). READ(B1 §2d): "sized" as a per-source optimization.
Failure modes: source-type mis-routing (must detect managed vs BYO); warehouse spin-up latency + per-query cost + a re-introduced Snowflake dependency; SQL-NULL/bag/datatype ↔ SPARQL/RDF semantic mismatch (READ(B1 §2a): Ontop's studied correctness surface — nulls, duplicates, datatype-correct term construction); the snapshot-pin seam above.
DataFusion relation: ORTHOGONAL/COMPLEMENTARY — DF ships a SQL unparser, so DF adoption makes THIS cheaper (lower one plan, then EITHER execute locally OR emit SQL, chosen per source-type — two backends for one lowered plan).

## 6. ADAPTIVE per-table promotion to a native TWIN (telemetry-driven; planner picks source per table)

Mechanism: telemetry flags hot tables; auto-materialize them into a SEPARATE native twin ledger + alias-repoint (per READ(C4): virtual and native are DISJOINT by construction — this is twin+repoint, NOT in-place conversion, and the disjointness guard must be lifted for it); the planner then picks native-vs-virtual PER TABLE. Includes the zero-telemetry STATIC special case worth calling out: dims-native (the 8 dims are ≤ a few M rows → they fit the EXISTING 40GB pack door AND a single restore window TODAY, READ(C3 §5 table)) + facts-virtual.
Rescues: **R6** for promoted tables (native pages from S3 via the leaflet cache — READ(C3 §3 RELAYED): eager set = root+manifests, cold cost scales with leaflets TOUCHED not ledger size — killing the cross-region Iceberg cold-catalog RTT); the DIM-SIDE of **R2** (a native dim is a fast paged lookup, removing the small-side scan + catalog RTT); dim-rollup families A/B; and native stats are INDEXED, so COUNT/point-lookup/min-max on a promoted table get fast (helps R4 for promoted tables).
Does NOT rescue: **R1** for a promoted BIG fact — a native 550M-row UNFILTERED GROUP BY still scans every row (READ(C3/00-MASTER §4): slow natively too); R3; the big-FACT-materialize term. So promotion is a FETCH/point/join-small-side lever, complementary to 3b/DataFusion for the big-rollup term.
Primitives vs net-new: RIDES #1422's watermark/incremental-sync engine (READ(C3 §1): the only DELTA engine — durable watermark, append-only windows, latest-by-key), solo's materialize SQS-FIFO + job-rows + self-reinvoke (C4), and the pack/restore door (C3) for tables that fit + direct-S3 build (C3 §3: uncapped, engine already supports S3+DynamoDB connections) for the 200M+ facts. NET-NEW and HEAVY = READ(C3 §10)'s 8 must-builds (rebase #1422 onto main ≥#1508, a hard-delete file-diff lane, twin lifecycle, alias-repoint, per-table source selection, freshness surfacing).
Consistency: the ONLY option that BREAKS snapshot-exactness — a synced twin is stale by the sync lag (READ(C3 §6): t advances per SYNC BATCH, mapping to some EARLIER Iceberg snapshot), and a MIXED query (native dim ⋈ virtual fact) reads TWO consistency points unless the planner pins both to a common snapshot (a real cross-source skew hazard). Plus the #1422 hard/COW-delete blind spot (READ(C3 §1): CDC-marker-only → ghost subjects never retract) and the pre-#1508 resurrection bug (READ(C3 §4): every currently-pinned engine still carries it; a twin must be cut from main ≥ `7581f0ac8`). Highest correctness risk of the slate.
Size: **XL** (sync engine + delete lane + twin lifecycle + alias-repoint + planner routing + telemetry).
Failure modes: sync-lag staleness with NO lastSync concept in solo today (READ(C3/C4)); hard-delete ghosts (V1-adjacent); resurrection if cut pre-#1508; mixed-source consistency skew; promote/demote thrash; twin storage cost; the disjointness guard lift.
DataFusion relation: ORTHOGONAL — promotion changes the SOURCE (Iceberg↔native); DF changes the EXECUTION engine; independent axes. DF REDUCES the pressure to promote (if live-virtual is fast enough, fewer tables need a twin).

## 7. Async / continuation query protocol (riding durable-turn + job-row primitives)

Mechanism: for known-heavy shapes, return a job-id + poll/stream instead of a synchronous 180s-bounded call; run to a higher bound (up to the 900s MCP turn budget, or across self-reinvokes for longer) and deliver into the durable turn.
Rescues: the UX CLIFF for any family that COMPLETES between 180s and 900s — the whole R1 band up to ~300M rows (357s < 900s), some R6 cold sweeps, R5-hybrid. It does NOT speed anything — an ENVELOPE lever. Precise envelope from READ(C1 §1b): the chat cap is now 180s WITH a 20s heartbeat (live-stream-visible), the MCP turn budget is 900s durable, the router default deadline 300s — so the classes needing async are those between 180s and 900s (durable-turn) and, for >900s, self-reinvoke continuation (the materialize resume-payload pattern).
Does NOT rescue: R2 (OOMs regardless of TIME → async just backgrounds a failure); anything >900s single-invoke without continuation; and it adds no capacity — a 590s job still burns 590s of Lambda.
Primitives vs net-new: RIDES solo's job-row scaffolding — READ(the strategy slate T1.5, C4 solo-pipeline facts §4): STATUS_TABLE, RECORD_TYPE_MATERIALIZATION, turn-completion endpoint, materialize self-reinvoke, UI turn-content polling — "assemble, not invent." NET-NEW = a query-as-job envelope (no async query path today — invoke_sync only), a heavy-shape ROUTER, deadline-bounded.
Consistency: pin the snapshot at job-SUBMIT; the async job reads that pinned snapshot → EXACTLY-correct, and the result is snapshot-keyed so it can ALSO populate #1's result cache (a natural pairing: async computes once, result-cache serves forever).
Size: **M** (solo assembly over existing primitives + the router). Hard dependency SATISFIED: READ(the strategy slate T1.5, C1 §4): async WITHOUT a deadline = the 900s runaway backgrounded; the deadline-everywhere work (S1/S3/T3.1) is now DEPLOYED, so the prerequisite is met.
Failure modes: job-row lifecycle/GC; surfacing "still running" gracefully vs a 504 (C4 solo-pipeline facts §4 the highest-leverage UX ask); cost of a heavy backgrounded job; >900s continuation state.
DataFusion relation: ORTHOGONAL — async wraps whatever computes; DF SHRINKS the band that needs async (as the live floor drops, fewer shapes exceed 180s). Complementary safety net.

## 8. Progressive / approximate answers (sampling + sketch-backed estimates, exactness-labeled)

Mechanism: for EXPLORATORY agent traffic, return a fast approximate answer — a deterministic-seeded sample of k-of-N files/row-groups for an estimated aggregate, or a sketch-backed estimate (HLL/Theta for COUNT-DISTINCT+NDV, reservoir for SUM/AVG with error bounds) — LABELED approximate, with an exact path on demand. WEB(https://iceberg.apache.org/puffin-spec/ , https://www.dremio.com/blog/puffins-and-icebergs-additional-stats-for-apache-iceberg-tables/): Puffin Theta sketches are single-pass, "orders of magnitude faster," and mergeable — the ready-made substrate.
Rescues: the LATENCY of R1 (sample → estimate in seconds; exact via 3b/#4/#7 if demanded), R4 (Σ record_count is already EXACT and instant; COUNT-DISTINCT via sketch), and R5's NDV (READ(A1/A3): `distinct_count` is hard-coded `None` today — a sketch fills the one stat the planner and get_data_model currently lack). The key fit: much of the deployed demand is the agent ORIENTING — "~39 exploratory rollups in one turn to understand the data" (READ(the strategy slate exec-summary)) — where a labeled ballpark is as useful as an exact sum and ~100× cheaper; this attacks DEMAND like #1 but for FIRST-time NOVEL queries.
Does NOT rescue: any request that NEEDS an exact answer (a final BI report) — it is an exploratory/triage lever; R2/R3 exact; correctness-sensitive traffic.
Primitives vs net-new: NET-NEW = a sampling scan mode (read k-of-N shards), sketch aggregates (or read Puffin Theta if the writer emitted them — else cheap to compute+merge), an EXACTNESS-LABEL in the result envelope, and MCP/prompt changes so the agent requests-and-accepts estimates (pairs with the P.1 product lever, READ(the strategy slate P.1)).
Consistency: a deterministic sample of snapshot S is a snapshot-keyed, bounded-error, exactly-REPRODUCIBLE estimate (§0 lemma); "error" is orthogonal to "staleness" — exact-for-a-sample-of-S, not stale. Theta/NDV from Puffin is snapshot-keyed.
Size: **M–L** (sampling scan + sketch aggregates + the labeling contract + agent-prompt work; Theta-from-Puffin is S IF the source writes Puffin — many don't).
Failure modes: an UNLABELED estimate mistaken for exact (the label is load-bearing — a discipline failure here is a silent-wrong-answer); sampling bias on skewed data (stratified sampling needed for SUM); error-bound honesty; the agent/user must be taught to consume "approx."
DataFusion relation: COMPLEMENTARY — DF ships sampling + approx aggregates (`approx_distinct` etc.), so DF adoption hands over the sketch machinery near-free.

## 9. Writer-side source-layout advisory (partition + compaction + clustering, pushed to the source) — [analyst addition]

Mechanism: rather than compute-side work, improve the SOURCE layout — advise/automate the customer (or Snowflake) to partition/cluster hot tables on the common filter/GROUP-BY columns and compact file counts — AND implement the currently-inert partition pruner so the layout starts winning. READ(A3/A1/V1): `can_contain_partition` is a NO-OP STUB (args underscore-unused, no caller) and manifest-summary pruning is unused, though all partition specs/transforms are already PARSED — so the engine half is bounded, prerequisite-complete work.
Rescues: **R6** (fewer/partition-skipped files → less fetch) and the FILTERED variants of R1 (a date-partitioned fact filtered by date reads one partition). READ(B1 §3b): "the largest missing standard Iceberg feature; HIGH impact on real partitioned BYO tables."
Does NOT rescue: UNFILTERED R1/R4 (partitioning cannot help a GROUP BY with no WHERE — every partition is read), R2, R3-without-a-partition-key, R5. Explicitly MINORITY-breadth for the deployed unfiltered-rollup majority — READ(the strategy slate T1.4/T3.5) DEMOTED partition/compaction for the SMOKE dataset specifically (Snowflake wrote EMPTY partition specs — READ(V1 2c) — so the pruner is doubly inert there); this option is for REAL customer tables, not the current test data.
Primitives vs net-new: db NET-NEW = implement the partition-pruner stub + manifest-summary pruning (bounded — all parsers exist). Customer-side = advisory/docs, or a Snowflake OPTIMIZE request — NOT Fluree-controlled (the standing the strategy slate caveat: the BYO bucket layout is customer-owned).
Consistency: NONE new — it changes the SOURCE layout, producing NEW snapshots each queried snapshot-exact. Orthogonal to consistency.
Size: **M** engine (partition-transform evaluation) + EXTERNAL (customer action, uncontrollable).
Failure modes: customer won't/can't re-lay-out their lake (the BYO reality); unpartitioned sources (inert); partition-column ≠ filter-column mismatch; compaction is a customer maintenance job.
DataFusion relation: COMPLEMENTARY — READ(B1 App-D2c): iceberg-rust's DataFusion `TableProvider` does partition pruning UPSTREAM, so adopting it later gets this "for free" vs hand-implementing the stub; the customer-side layout advisory is engine-independent.

## 10. Partial / intermediate-result reuse (snapshot-keyed sub-result cache: dim-lookups + grouped-FK partials) — [analyst addition]

Mechanism: cache not the FINAL result but reusable INTERMEDIATES keyed by (snapshot, sub-plan-hash) — decoded dimension-lookup tables, grouped-by-FK partial aggregates, scan-file selections. This is the existing per-QUERY memos (READ(A1 §3, caches #11–#13): parent-lookup memo, per-op scan cache) WIDENED to per-session/cross-query scope and moved to the shared tier (#2).
Rescues: the WITHIN-TURN + cross-query OVERLAP that #1's final-result cache MISSES — the "~39 distinct rollups in one turn" (READ(the strategy slate exec-summary)) all scan the same few dims and many share the same fact→dim FK-grouping partials, so rollup #2..#39 become partial-REUSE instead of 39 cold scans. Attacks the reuse slice of R1 (shared fact scan / FK partials), dim-rollups (shared dim decode), and the dim side of R2.
Does NOT rescue: a single novel query's FIRST compute (a reuse lever, like #1); families that share no sub-structure (R3 VALUES, R4 COUNT).
Primitives vs net-new: RIDES the engine's existing per-query memos (A1 #11–13). NET-NEW = widen their KEY to (snapshot, sub-plan) + their SCOPE cross-query, and wire to #2's shared tier (cross-container reuse REQUIRES #2 — within a turn, concurrent rollups fan across non-sharing containers under the cap-2 semaphore, READ(C1 §1d, C4 solo-pipeline facts §4)). So #10 is #2's substrate applied to COMPUTED intermediates, not raw bytes.
Consistency: snapshot-keyed intermediates = EXACTLY-correct (§0 lemma); a dim-lookup for S is a pure function of S. MoR caveat inherited if computed delete-ignoring (gate the build).
Size: **M** (widen memo key/scope + shared-tier wiring + decide what's worth caching — dim tables yes, giant fact partials maybe).
Failure modes: intermediate size (a decoded dim is bigger than its result); sub-plan-hash canonicalization (harder than a full-query hash); policy/tenant isolation (as #1); LOW cross-container hit rate without #2.
DataFusion relation: COMPLEMENTARY — DF has no cross-query cache; this sits above it (DF makes each partial cheap; reuse makes the 2nd..Nth free).

## 11. Closing — dominance and synergy relations (NOT a ranking)

DOMINANCE (the key scoping result): **sidecar cubes (3b) strictly dominate full native materialization (strategy b) for the R1 rollup family** — a native twin STILL full-scans a 550M-row unfiltered GROUP BY (READ(C3/00-MASTER §4)), while a per-snapshot cube is O(1); the twin's advantages (fetch, point-lookup, join-small-side) are exactly R6/R2-small-side, which #6 promotion serves without needing the whole star. So "materialize the rollup answer (cube), not the rollup input (twin)."
SYNERGY 1 — **snapshot-keyed correctness is the shared enabler**: options 1, 3, 8, 10 (and 4/7's result-population) all inherit the deployed per-query snapshot-pin's EXACTNESS for free (§0 lemma) — a per-snapshot artifact is a pure function of an immutable snapshot, so the ONLY staleness axis is the already-shipped pointer-TTL — EXCEPT #6 (twin sync), the one option that breaks snapshot-exactness and additionally inherits #1422's delete/resurrection risk. This is why the "third way" is cheap to make CORRECT, and why #6 is the correctness-expensive outlier.
SYNERGY 2 — **the cold/scale stack composes multiplicatively**: DataFusion (execution: 56k→vectorized) × MPP #4 (horizontal: past 6 vCPU) × warm-tier #2 (fetch: dissolve R6) × sidecar/cube #3 + result-cache #1 + partial-reuse #10 (demand: answer without compute) × async #7 (envelope). Each attacks a DIFFERENT term of `wall ≈ rows/(56k×cores)` + fetch-floor + repeat-demand; e.g. #4 builds the #3b cube that #1 then serves forever, populated behind #7, read cold from #2, with each worker running DataFusion. No pair is redundant.
SYNERGY 3 — **DataFusion Step-1 is the multiplier that SHRINKS every other option's burden**: by dropping the live floor it shrinks the band needing async #7, the tables needing promotion #6, and the rollups needing cubes #3b — but it does NOT own the extreme tail (the 550M O(1) cube, cross-container cold R6, exact repeat-demand R5) that the caching/sidecar/MPP options own; so it is necessary-not-sufficient, exactly as READ(B1 §5c) concludes.
AXIS COMPLETENESS (the honest closing frame for the ranking): the deployed residual needs at least one DEMAND lever (1/3b/8/10/P.1), one CAPACITY lever (DataFusion/2/4/6), and the ENVELOPE lever (7) — the cheapest COMPLETE combination that touches all of R1–R6 is INFERRED to be {3a stats-sidecar (R4/R5), 3b cube (R1), #1 result-cache + #10 partial-reuse (repeat-demand across all), #2 warm-tier (R6), #7 async (envelope to first-populate) } — with DataFusion Step-1 as the capacity multiplier under all of them and #4 MPP reserved for the build jobs the single-Lambda wall can't do; #5 is a Snowflake-segment-only bonus and #6/#9 are heavier/externally-gated bets to weigh against that core.
