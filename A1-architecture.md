# A1 — Virtual Dataset (R2RML / Iceberg / S3-Parquet) Architecture & Data-Flow Map

## 0. Scope, method, provenance

This is the definitive architecture + data-flow map of fluree/db's "virtual dataset" read path — SPARQL/JSON-LD over R2RML-mapped Iceberg tables in S3 — at the audit tip `origin/feat/lambda-usability = 10e073fe9` (PR #1514), read in the detached read-only checkout `<audit-checkout>`. Receipts are `path:line` relative to that checkout; claims are labelled `READ(file:line)` when observed directly and `INFERRED` when reasoned. Method: I traced the query-side spine (entry → planner/rewrite → operators → provider seam) directly, and separately deep-read the Iceberg engine (catalog/IO/decode/scan-fold), the cache inventory, and the concurrency/memory model; every receipt below was cross-checked against the churn and the current tree.

The virtual path is a distinct, self-contained subsystem grafted onto Fluree's native triple engine. It is gated by the `iceberg` cargo feature (`fluree-db-api/src/graph_source/mod.rs:114-142` READ), and it reaches the storage/format layer through the standalone `fluree-db-iceberg` crate (a hand-rolled Iceberg client — not `apache/iceberg-rust`) plus `apache_avro` for manifests and `parquet`+`arrow` for data files. The single most important structural fact: there is a hard trait seam at the `fluree-db-query` ⇄ `fluree-db-api` boundary — the query engine defines `R2rmlProvider` / `R2rmlTableProvider` (`fluree-db-query/src/r2rml/provider.rs:134,182` READ) and the API layer implements them as `FlureeR2rmlProvider` (`fluree-db-api/src/graph_source/r2rml.rs:591,618,794` READ). Everything columnar (Iceberg, S3, Parquet, credentials, disk caches) lives below that seam; everything triple-oriented (rewrite, operators, folds) lives above it and only ever sees `ColumnBatch` streams.

## 1. Module map (crate-by-crate, virtual path only)

- `fluree-db-iceberg` — the columnar engine. `catalog/{rest,direct}.rs` (loadTable over an SSRF-hardened `reqwest` client); `auth/{oauth2,bearer,mod}.rs` (catalog HTTP auth); `credential/{vended,aws_provider}.rs` (S3 data-plane creds); `metadata/{table,snapshot}.rs` + `manifest/{manifest_list,data_file,value_codec}.rs` (Iceberg JSON + Avro decode); `scan/{planner,send_planner,pruning,predicate,topk}.rs` (file/row-group pruning fold); `io/{storage,parquet,send_parquet,arrow_reader,chunk_reader}.rs` (`aws-sdk-s3` GETs + Parquet/Arrow decode); `stats.rs` (manifest-only metadata aggregation). Two parallel trait families run throughout: a `?Send` WASM set (`ParquetReader`, `IcebergStorage`, `ScanPlanner`) and a `Send+Sync` server set (`SendParquetReader`, `SendIcebergStorage`, `SendScanPlanner`), the latter `#[cfg(feature="aws")]` — the live server path is entirely the `Send`/`aws` set (READ `fluree-db-iceberg/src/lib.rs:83-94`, `io/mod.rs:11-31`).
- `fluree-db-r2rml` — the mapping model, independent of Iceberg. `loader/` (parse R2RML Turtle/JSON-LD → `CompiledR2rmlMapping`), `mapping/{triples_map,term_map,ref_object_map,compiled}.rs` (the compiled structures the operator reads), `materialize/term.rs` (column value → `RdfTerm`), and `emit/` (the reverse direction: auto-generate an R2RML mapping from Iceberg metadata — the "generate" UX, not the read path).
- `fluree-db-query/src/r2rml/` — the query-side of the seam. `provider.rs` (the two provider traits + the pushdown vocabulary `ScanFilter`/`ScanValue`/`ScanTopK`/`ObjectConstant`), `rewrite.rs` (triple-pattern → `R2rmlPattern` IR rewrite: class fusion, star pruning, ref-target pruning, budget forwarding), `operator.rs` (`R2rmlScanOperator` — the streaming materializer), `fused_aggregate.rs` (`FusedR2rmlAggregateOperator` — COUNT/SUM/AVG folded straight from column batches, plus the manifest-COUNT shortcut).
- `fluree-db-api/src/graph_source/` — the API-side of the seam and the catalog glue. `r2rml.rs` (`FlureeR2rmlProvider`: `scan_table`/`table_row_count`/`compiled_mapping`/`prefetch_tables`, plus `load_table_context` and `scan_table_inner`), `catalog_session.rs` (per-query snapshot-pin machinery), `cache.rs` (the in-memory moka cache family), `disk_catalog_cache.rs` (persistent cross-process catalog + pointer cache), `lazy_storage.rs` (`LazyS3Storage` deferred-credential storage), `iceberg_catalog.rs` (browse/preview/verify for the UX), `crawl.rs` (the entity-crawl/"detail" path used by chat), `iceberg_generate.rs`/`iceberg_sample.rs`/`iceberg_validate.rs` (the generate/sample/validate UX), `config.rs` (the Iceberg graph-source config model), `ephemeral.rs` (register-less one-shot queries).
- Entry glue outside `graph_source/`: `fluree-db-api/src/graph_query_builder.rs` (the `GraphQueryBuilder.with_r2rml()` builder + graph-source fallback), `fluree-db-query/src/execute/runner.rs` (attaches providers to `ExecutionContext`, precomputes `r2rml_graph_ids`), `fluree-db-query/src/graph.rs` (`GraphOperator` invokes the rewrite), `fluree-db-query/src/execute/{operator_tree,where_plan}.rs` (build the fused-aggregate / scan operators), `fluree-db-query/src/context.rs` (`ExecutionContext` carries the providers + the memory budget + checkpoint).

## 2. End-to-end read path (representative query)

Representative query: a chat/BI `SELECT ?p ?name WHERE { ?p a edw:Product ; edw:name ?name } LIMIT 20`, executed as a `FROM <enterprise>` dataset query against a REST-catalog (Snowflake Horizon / Polaris) Iceberg table with vended S3 credentials. This exercises the whole spine; a fact⋈dim star or a `COUNT(*)` diverges only at the operator-selection step (§2 step 4).

1. Entry + provider attach. The API builds a `GraphQueryBuilder`, and `.with_r2rml(provider)` stores `(R2rmlProvider, R2rmlTableProvider)` on the builder core (READ `graph_query_builder.rs:120-123`). If the named ledger doesn't exist as a native ledger, a graph-source fallback synthesizes a genesis `GraphDb` with `graph_source_id` set, guarded by `has_r2rml_mapping` (READ `graph_query_builder.rs:153-175`). Execution enters `runner.rs::execute_prepared`, which attaches the providers to the `ExecutionContext` via `with_r2rml_providers` (READ `runner.rs:837-839`), wires the cancellation handle (READ `runner.rs:828-829`), and — the key dataset-mode step — precomputes `ctx.r2rml_graph_ids` by calling `provider.has_r2rml_mapping(...)` for every default + named graph in the dataset (READ `runner.rs:872-900`). This set is how downstream operators recognize an R2RML-backed graph without another async round-trip.

2. Plan / dispatch. `build_operator_tree_inner` (in `execute/operator_tree.rs`) first tries fast paths: if the query is a foldable aggregate over one R2RML source, `detect_fused_r2rml_aggregate(query)` returns a plan and the tree becomes a `FusedR2rmlAggregateOperator` wrapping a stripped-down fallback, with HAVING/ORDER/OFFSET/LIMIT re-applied on top (READ `execute/operator_tree.rs:2473-2511`). Otherwise the `GRAPH`/dataset patterns route through `GraphOperator` (`graph.rs`), which checks `ctx.r2rml_provider` + `has_r2rml_mapping` (READ `graph.rs:278-279`) and calls `rewrite_patterns_for_r2rml(...)` to convert the contained triple patterns into an `R2rmlPattern` IR (READ `graph.rs:288,498`). `where_plan.rs` then instantiates `R2rmlScanOperator::new(child, pattern)` (READ `execute/where_plan.rs:2419`). The `LIMIT 20` is forwarded through the row-preserving wrappers: `DatasetOperator` forwards it (T1.3, gated `FLUREE_R2RML_DATASET_BUDGET`, READ `r2rml/mod.rs:69-84`), and `set_row_budget` lands it on the scan operator (READ `operator.rs:2549-2559`).

3. Operator open. `R2rmlScanOperator::open` opens its child seed, then loads the compiled mapping via `provider.compiled_mapping(graph_source_id, as_of_t)` — and critically passes `as_of_t = None` in dataset mode (READ `operator.rs:2571-2593`), because there is no meaningful cross-ledger `t`. `compiled_mapping` on the API side resolves the graph-source record from the nameservice, compiles the R2RML source (memoized), and returns `Arc<CompiledR2rmlMapping>` (READ `r2rml.rs:650`, cache at `cache.rs:198-205`).

4. Pull loop. `R2rmlScanOperator::next_batch` is a pull-based streaming loop that materializes one window at a time so the whole table is never resident (READ `operator.rs:2599-2705`): it drains pending overflow, emits once a `batch_size` window is full OR the LIMIT budget is optimistically met (READ `operator.rs:2631-2660`), advances an in-flight scan by one window (`advance_one_window`, READ `operator.rs:2665-2672`), or pulls the next child batch and starts a scan via `build_progress` (READ `operator.rs:2676-2681`). A cancellation checkpoint runs at the top of the loop (READ `operator.rs:2616`, `check_cancelled`) plus a second poll before each batch decode (READ `operator.rs:1400`). `build_progress` calls `provider.scan_table(gsid, table, projection, filters, topk, as_of_t)` — the seam crossing.

5. Provider `scan_table` → `load_table_context` resolution ladder. `scan_table` wraps `scan_table_inner` in an `r2rml.scan_table` span (READ `r2rml.rs:801-831`). `scan_table_inner` first resolves the pinned table context via `load_table_context` (READ `r2rml.rs:1773-1774`). That ladder (READ `r2rml.rs:1274-1465`): look up the graph-source record + parse `IcebergGsConfig`; compute `lt_key = gsid␟ns.table`; for a REST catalog, consult (a) the per-query session pin `pinned_metadata_location(lt_key)` then (b) the disk pointer `disk.get_metadata_location(lt_key, None)` (READ `r2rml.rs:1351-1354`); on a hit, pin the location, build/reuse the process-wide REST client with NO network (the OAuth exchange rides the first real catalog op), and return a `LazyS3Storage::deferred(builder)` whose credential-bearing S3 build is deferred until an actual data-file fetch (READ `r2rml.rs:1355-1457`). On a miss it falls through to an eager `loadTable` GET + storage build (READ `r2rml.rs:1465+`, via `resolve_rest_load_and_storage` at `r2rml.rs:1065`). The `_as_of_t` argument is deliberately ignored — time-travel is not implemented (READ `r2rml.rs:1759-1762`, GREP marker `r2rml-as-of-t`).

6. Scan planning + file pruning. Back in `scan_table_inner`: resolve projection column names → Iceberg field-ids (READ `r2rml.rs:1797-1809`); build an Iceberg pushdown `Expression` from the `ScanFilter`s via `build_iceberg_filter` (READ `r2rml.rs:1823`, def at `r2rml.rs:158`); then select data files. If a pushdown filter is present, run `SendScanPlanner::new(storage, metadata, scan_config).plan_scan()` fresh (READ `r2rml.rs:1830-1846`); otherwise consult the scan-files cache tiers (in-memory moka `cache.get_scan_files` → disk `catalog_disk_cache().get_scan_files` → compute) keyed by the immutable `metadata_location` (READ `r2rml.rs:1847-1886`). The planner selects `current_snapshot()`, reads the manifest-list + manifests (Avro), and per data file applies `can_contain_file` min/max pruning, yielding `FileScanTask`s (READ `scan/planner.rs:180-274`, `send_planner.rs:38-156`, pruning at `scan/pruning.rs:78-138`). See §4.

7. Data-file fan-out + Parquet decode. `scan_table_inner` fans the surviving tasks out with `buffer_unordered(iceberg_scan_concurrency(tasks.len()))`, each file read inside a `tokio::spawn(SendParquetReader::with_caches(...).read_task(task))` with a per-file span and a row-group-concurrency budget (READ `r2rml.rs:2123,2157,2164,2183`; concurrency helper `r2rml.rs:72-84`). If a scan-side top-k directive is present, a separate sequential-prefix + parallel-tail path runs `plan_topk_read` and stops early via the `TopKBound` (READ `r2rml.rs:1979-2115`). Each `read_task` reads the footer (from the footer cache, or sliced out of already-in-memory whole-file bytes when `FLUREE_ICEBERG_FOOTER_FROM_CACHE` is on), computes `surviving_row_groups` from row-group stats, and calls `decode_batches_arrow` with a `ProjectionMask` of the projected leaves, `with_row_groups(surviving)`, and a post-decode `filter_record_batch` (READ `io/send_parquet.rs:406-482,742-823,168-186`, `io/arrow_reader.rs:80-249`). Bytes come from `aws-sdk-s3` range GETs (`io/storage.rs:418-447` READ) or the on-disk `DiskArtifactCache` (READ `r2rml.rs:1780-1781`). Output is a `Stream<Item=Result<ColumnBatch>>` (`ColumnBatchStream`).

8. Triple materialization + engine folds. The operator consumes the `ColumnBatch` stream and materializes RDF terms per the mapping in `materialize_batch` (READ `operator.rs:2155`) — subject IRI from the subject template, predicate IRIs from the POMs, objects from columns via `materialize_pom_object` (READ `operator.rs:1909`), enforcing constant-object constraints (`row_passes_star_constraints`, READ `operator.rs:2115`) and any consumed FILTER (READ `operator.rs:504-507`). RefObjectMap joins to parent/dimension tables are resolved through `build_parent_lookup` (READ `operator.rs:2498`) with cross-batch memoization (`parent_lookup_cache` + the query-scoped `R2rmlParentMemo`). The materialized bindings then flow up the ordinary engine operator tree — joins (`hash_join.rs`), OPTIONAL (`optional.rs`), GROUP BY (`group_aggregate.rs`), SORT/LIMIT — and out through serialization. For the fused-aggregate shape, steps 4–8 collapse: `FusedR2rmlAggregateOperator` folds COUNT/SUM/AVG straight from the `ColumnBatch`es (READ `fused_aggregate.rs:503,843`), and for a bare `COUNT(*)` it may skip data files entirely via `table_row_count` reading the manifest `record_count` sum (READ `r2rml.rs:843-865`, trait contract `provider.rs:217-241`).

Not a cache, a switch: `FLUREE_ICEBERG_FOOTER_FROM_CACHE` (default on, READ `send_parquet.rs:177`) — slices the Parquet footer out of already-in-memory whole-file bytes instead of a separate 2-GET footer round-trip. Correctness properties worth stating: the content-addressed layers (#2, #3, #7, and #14's metadata/scanfiles/countstats) can never go stale because their key IS the immutable snapshot's `metadata_location`/path (READ `disk_catalog_cache.rs:5-8`). The mutable layers are exactly the ones with TTLs: the pointer (#14, 300s), the cross-query loadTable (#6, 60s), the REST client (#5, 900s), and the Direct version-hint (#4, 2s). The **no-credentials-on-disk** hard constraint is structurally enforced: the disk pointer struct has exactly three fields `{metadata_location: String, snapshot_ms: i64, cached_at_ms: u64}` (READ `disk_catalog_cache.rs:165-174`) with a test scanning the written bytes for credential substrings (READ `disk_catalog_cache.rs:682-720`); the credential-less `location_pins` map (#10) is kept separate from the credential-bearing `load_tables` map (#8) precisely so `cached_load_table` can never serve a creds-None entry that would build ambient-credential storage (READ `catalog_session.rs:99-108,170-188`). The per-query pin (#8/#10) is the correctness core: it guarantees every scan in one query reads ONE Iceberg snapshot even if the table commits mid-query, and the read path pins the location BEFORE serving from the disk pointer so a mid-query pointer-TTL expiry still resolves the pinned snapshot (READ `catalog_session.rs:13-16`, `r2rml.rs:1355-1364`).

## 4. Scan-planning fold (stats-driven pruning, types, partitions, deletes, schema-evolution, snapshot, top-k)

Two conservative (strict-superset) pruning layers exist, at different granularities. (a) Manifest DataFile-bounds pruning, wired into the planner: `can_contain_file(expr, data_file, schema)` decodes each file's `lower_bound`/`upper_bound` for the predicate field and reasons over min/max per operator (READ `scan/pruning.rs:78-138`, decode `manifest/value_codec.rs:207-324`). The types that participate at this level: `boolean,int(i32),long(i64),float,double,date,timestamp,timestamptz,string,binary/fixed,uuid,decimal(p,s)` — the full set, little-endian per spec except big-endian decimal (READ `value_codec.rs:207-324`); `NotIn` and any unknown type fall back to conservative keep (READ `pruning.rs:132-136`). (b) Parquet row-group stats pruning, applied inside the Arrow decode: `row_group_can_contain` reads parquet-rs `Statistics` (READ `pruning.rs:211-262`). This layer is narrower — `stat_bounds` handles `Boolean, Int32, Int32→Date, Int64, Double, Float, FLBA→Decimal, ByteArray→String`, and it explicitly declines INT32/INT64-backed decimals (only FLBA-decimals are spec-safe, per fluree/db #1406, READ `pruning.rs:277-294`). Notable asymmetry (READ): there is **no Timestamp arm at the row-group level** — a timestamp predicate (physically int64) is pruned at the manifest level (a) but NOT at the row-group level (b), where it falls through to keep.

The pushdown vocabulary the operator emits is deliberately narrow and correctness-preserving: `ScanValue` = Bool/Int/Date/Str plus Double + Decimal (the last two gated by `FLUREE_ICEBERG_NUMERIC_STATS`, PR-7), plus `TemplateKey` for bound-subject pushdown (READ `provider.rs:44-70`). The doc-contract is explicit that a missed push is never wrong — the in-engine FILTER remains authoritative (READ `provider.rs:41-43,96-104`). Numeric-stats pushdown is gated so the whole iceberg-side widening (new `stat_bounds` arms + FLBA-decimal relax) stays inert when off, because no numeric `LiteralValue` is ever produced at the single push site (READ `r2rml/mod.rs:96-107`).

Conspicuous gaps in the fold, all honest and receipted (INFERRED consequences noted). Time-travel `as_of` is DEAD CODE end-to-end: `select_snapshot(SnapshotSelection::AsOfTime)` is fully implemented but has no caller, `ScanConfig` has no snapshot field, and both planner entry points hardwire `current_snapshot()` (READ `metadata/snapshot.rs:127-146`, `scan/planner.rs:19-30,181-184`; cross-repo grep confirms `fluree-db-api` never calls it). Partition pruning is ABSENT: `can_contain_partition` is a stub with underscore-unused params that returns `true`, and it has no caller; partition transforms (identity/bucket/truncate/day/hour) are parsed into the struct but never interpreted (READ `pruning.rs:32-66`, `metadata/table.rs:194`). Merge-on-read deletes are DETECTED BUT IGNORED: delete manifests (`content==1`) are filtered out of the manifest list, and the stats path parses them only to flag `has_delete_manifests` — they are never applied, so a scan can return rows a position/equality delete has logically removed (READ `manifest_list.rs:178-185`, `stats.rs:308-351`; INFERRED consequence). v1 tables are unsupported for scanning (no `manifest_list` → hard error, READ `planner.rs:203-207`). Schema evolution IS handled correctly and field-id-based: projection maps Iceberg field-ids → Parquet columns via embedded `field_id`, falling back to name-matching only for non-Iceberg files, and an Iceberg field absent from a Parquet file materializes as an all-null column (READ `parquet.rs:1269-1436`). Scan-side top-k (PR-5) is real end-to-end: the `topk.rs` toolkit (min-heap `TopKBound`, files ordered DESC by `upper_bound(sort_field)`, `can_stop` when the heap is full and the next file's upper bound can't beat the k-th) is driven by the operator's read loop (READ `scan/topk.rs:31-162`, engine drive `r2rml.rs:1979-2038`); it is DESC-only (ASC declined because SPARQL orders unbound values first, READ `topk.rs:22-23`).

## 5. Concurrency + memory / cancellation model

File-level parallelism: surviving data-file tasks are read through `buffer_unordered(concurrency)` where `concurrency = iceberg_scan_concurrency(tasks.len())` = `min(available_parallelism, num_files).clamp(1,32)` by default, overridable (and uncapped past the file count) by `FLUREE_ICEBERG_SCAN_CONCURRENCY` (READ `r2rml.rs:72-84,2123,2183`). Each file read is a `tokio::spawn` (READ `r2rml.rs:2157`). Catalog HTTP is bounded separately by a process-wide `tokio::Semaphore` default 8 via `FLUREE_ICEBERG_CATALOG_CONCURRENCY`, acquired around every loadTable GET and its 429/503 backoff, dropped before the token-refresh recursion to avoid a single-permit deadlock (READ `catalog/rest.rs:52,62-72,182,205-209`). Row-group parallelism (C4): a single large file's row groups are decoded across `spawn_blocking` tasks with degree `(available_parallelism/file_concurrency).max(1)`, gated `FLUREE_ICEBERG_ROWGROUP_PARALLELISM` (default on) and reached only for files >64MB with >1 row group (READ `r2rml.rs:2128-2132`, `send_parquet.rs:194-205,742-823,476`). vCPU detection is `std::thread::available_parallelism` only — NO `num_cpus`, and NO CPU-cgroup-quota reading, so a container with a fractional CPU limit still sees the host core count (READ `r2rml.rs:80,2128`; INFERRED for the cgroup gap). The `send_`-prefixed engine files exist because the standard parquet reader futures are `?Send` for WASM while the query `Operator` trait needs `Send`; the sync decode ↔ async storage bridge is runtime-flavor-aware (`block_in_place` on multi-thread, a fresh helper OS-thread+runtime on current-thread) (READ `send_parquet.rs:1-14`, `chunk_reader.rs:118-166`).

Memory + cancellation (the R3 work). The typed memory budget is `query_memory_budget_bytes()` = `FLUREE_QUERY_MEMORY_BUDGET_BYTES` override (0 disables), else ~78% of the detected container limit, else an 8 GiB fallback; container detection reads cgroup v2 `/sys/fs/cgroup/memory.max` → cgroup v1 `memory.limit_in_bytes` → `/proc/meminfo` (READ `context.rs:35-50,64-88`). `checkpoint()` checks cancellation first, then compares tracked `used` against the budget, raising `MemoryBudgetExceeded` (READ `context.rs:780-796`). The cancellation handle is a pure externally-signalled atomic flag with NO internal deadline — a timeout only exists because the server spawns a wall-clock watchdog (`FLUREE_QUERY_TIMEOUT_MS`, default 15 min) that calls `cancel_with(Timeout)`, threaded to the operator's ctx (READ `fluree-db-core/src/cancellation.rs:64-77`, `fluree-db-server/src/query_control.rs:57-77`, `runner.rs:828-829`). The critical enforcement gap: only aggregating/joining operators feed the budget counter — `record_alloc` is called only in `group_aggregate.rs`, `hash_join.rs`, and `fused_aggregate.rs` (READ), and `checkpoint()` (budget-aware) is called on the virtual path only inside `fused_aggregate.rs:1182,2205,2282`. The plain `R2rmlScanOperator` materialize path uses `check_cancelled()` only (READ `operator.rs:955,1158,1400,1484,1534,2616`) and never `record_alloc`s its window, so a wide non-aggregate crawl's resident bindings AND the `O(concurrency)` in-flight scan-file buffers (≤32/64 MB each) are entirely invisible to the memory budget (READ + INFERRED). And `set_memory_limit` has no non-test callers, so no per-query ceiling is ever pinned — every concurrent query independently sees the full ~78% budget (INFERRED from grep). Enforcement map: file/catalog/row-group concurrency are cleanly bounded; deadline + cancellation are enforced cooperatively BETWEEN Parquet batches (`operator.rs:1400`) but NOT inside a blocking Arrow decode (`spawn_blocking`, no poll) or inside an S3 GET; the memory budget is enforced ONLY on aggregating/joining operators, conspicuously not on the plain crawl/materialize path.

## 7. Editorial — fragility, duplication, layering (honest, receipts required)

Columnar logic inside a triple-oriented operator (the central against-the-grain tension). The `R2rmlScanOperator` and especially `fused_aggregate.rs` reach deep into columnar concerns that would normally live below the seam. The fused operator hand-rolls COUNT/SUM/AVG folds, a BigDecimal arithmetic pipeline, and a fact⋈dim GROUP BY join directly over `ColumnBatch`es (READ `fused_aggregate.rs:471-679,764-799`), and it also owns the `record_alloc` memory accounting — meaning the ONLY place the memory budget is enforced on the virtual path is a bespoke aggregate operator, not a shared layer (READ §5). This is a lot of columnar machinery grafted onto the query engine because the seam exposes only row-at-a-time `scan_table`; a cleaner design would push aggregation/top-k into the `fluree-db-iceberg` scan as first-class operations rather than re-deriving them above the seam. It works and is well-tested, but it is the structural weak point: the two worlds (columnar/relational vs triple/graph) meet inside operators that were built for the latter.

Gate sprawl. There are ~23 `FLUREE_*` switches on this path (`FLUREE_R2RML_*` ×11, `FLUREE_ICEBERG_*` ×12), most defaulting on and each guarding one perf increment (READ the env grep; `r2rml/mod.rs:48-107` documents the R2RML family). This is a deliberate differential-hygiene discipline (an OFF run reproduces pre-change behavior for A/B verification, per the doc comments) and the falsy-spelling set is centralized (`env_switch_enabled`, READ `r2rml/mod.rs:48-56`) — but it is a large, mostly-invisible configuration surface that a production operator will never tune and that multiplies the tested state space. Several switches are effectively permanent-on scaffolding whose OFF path exists only for the audit.

Triple-tiered loadTable staleness (fragile-by-construction, mitigated). One table's current snapshot is resolvable from three independent layers with three different staleness windows: the per-query pin (#8/#10, zero staleness in-query), the cross-query moka (#6, ≤60s), and the disk pointer (#14, ≤300s) (READ §3). This is intentional bounded-staleness tiering and the pin-before-serve ordering closes the obvious mid-query hazard, but it is three TTLs guarding one fact, and the as-of-t rider that would make it time-travel-safe is present-but-dormant (`min_snapshot_ms` is `None` everywhere, READ `r2rml.rs:1354`, GREP `r2rml-as-of-t`) — a latent trap flagged in-code for whenever time-travel lands.

Two disk caches, asymmetric budgeting. #15 (artifact bytes) honors `FLUREE_DISK_CACHE_BUDGET_BYTES` and evicts continuously to an 80% low-water mark; #14 (catalog) has its own hardcoded 512MB cap pruned only ONCE per process at startup via a `OnceLock` (READ `disk_catalog_cache.rs:239,305-308`). A long-running process that writes >512MB of catalog entries (the doc's own ~7,670-file scanfiles example is large) after startup exceeds the cap until restart — a plausible slow-leak on a busy multi-table deployment.

Dead / dormant code that reads as "supported" but isn't. Time-travel `select_snapshot` (fully implemented, zero callers), partition pruning (`can_contain_partition` stub, zero callers), merge-on-read deletes (detected, never applied — a correctness risk, not just perf), `VendedAwsCredentialProvider` (dynamic-refresh S3 creds, only test constructors), and NDV/distinct-count (always `None`) all present as structured, tested code that a casual reader would assume is live (READ §4, §3). The delete-file gap is the one with a correctness edge: on a Snowflake/Iceberg table using merge-on-read, results can include logically-deleted rows (INFERRED from `manifest_list.rs:178-185`).

Duplication and boundary awkwardness worth a look. The `?Send` vs `Send` trait duality doubles the reader/planner/storage surface (`ParquetReader`/`SendParquetReader`, etc.) — necessary for WASM but a real maintenance tax, and the live server only ever exercises the `Send` half. The `read_ranges` per-object semaphore in `io/storage.rs:450-476` has no callers (the live scan bounds concurrency above the seam) — dead in the server path (READ). And the parent-lookup memo exists in THREE forms (#11 query-scoped `R2rmlParentMemo`, #13 per-operator cache, and the inner-scan replay #12) because correlated joins re-enter `build_progress` at different lifetimes (per-query vs per-operator vs per-child-batch); the layering is correct and each is load-bearing (the comments explain the q008/q031/q050 seams they each fix), but it is three memos guarding overlapping work and is the kind of thing that accretes one PR at a time. None of these are bugs; they are the honest cost of bolting a high-performance columnar reader onto a triple engine through a deliberately thin seam, one stacked PR at a time.
