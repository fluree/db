## 0. Executive summary

**The baseline does not need fundamental renegotiation.** The R2RML/Iceberg/S3-Parquet representations, wire handling, and IO/pruning layer are standard and correctly built (A1/B1); parity is byte-exact on every deterministic corpus query at both engines (C2: 0 hash mismatches, 45/45 deterministic queries byte-identical native==virtual); the caching architecture is stale-proof where it must be (content-addressed + snapshot-pinned) with staleness confined to four TTL'd layers.

**The strategies are validated where they apply — emphatically.** When a shape is admitted to a fast path, the machinery wins: fused aggregation escapes the per-row materialization regime (144.8× wall vs the same un-fused shape; 11.7×/core marginal throughput; beats native on q014), admitted pruning removes 100% of files, LIMIT-budget forwarding holds at 200× scale (SF20 reads 7,675→322), and 88% of the corpus runs ≤3s hot at sf01. The optimization program's individual mechanisms are sound, adversarially reviewed, and empirically confirmed.

**Coverage — not strategy — is the audit's central deficit.** Every member of the ≥3s tail and both SF20 DNFs are ADMISSION gaps, not engine ceilings: ~18 uncovered cliffs where a shape misses a gate and falls to full-scan per-row materialization (VALUES/IN never lowered; ASC top-k absent; OPTIONAL swallows budgets — 68,828× measured read amplification; MIN/MAX/COUNT-DISTINCT/GROUP_CONCAT decline; filtered COUNT loses the manifest shortcut for an 886× penalty; fact⋈fact declines; partition pruning inert). These cliffs are cache-immune (q038 cold≈warm) — only admission work cures them — and surface-independent (C2b: JSON-LD and SPARQL share IR and fail byte-identically, so each fix lifts both surfaces).

**Correctness: three findings demand action before further perf work.** (1) Merge-on-read delete files are silently ignored — correct today on append-only Snowflake CoW data, silently wrong the day MoR arrives (external writers default to it; a pending Snowflake BCR may flip managed tables) — fail-closed guard specified at the snapshot-selection choke point. (2) The #1508 retraction-resurrection fix is on main but NOT in the perf line or any deployed pin — mandatory merge-up. (3) The typed memory budget has a verified blind spot on the non-aggregate scan path (a real production OOM specimen lives there; ~4.4-11GB unaccounted worst-case; no per-query division) — solo's RSS watchdog remains load-bearing, contrary to the post-wave-4 ops narrative.

**Serverless: the envelope is better than documented, and the walls are named.** Wave-4 deployed the 180s chat cap + heartbeat + 300s universal deadline (docs lagged reality); the families still over the wall each have a matched cure: un-fused rollups → admission widening; 2-FACT joins → spill/semi-join (the DataFusion Step-2 territory); crawl/point-lookup at scale → the native-twin lever; whole-dataset COUNT → fused-manifest-COUNT; repeat BI demand → snapshot-keyed caches/cubes (exactly-correct by construction under the existing per-query snapshot pin — the audit's cheapest structural insight).

**Materialization (strategy b) is viable but should be scoped, not defaulted.** The serving half already exists (native ledgers page on-demand from S3 — a SF20-scale twin needs no local copy; solo restores prebuilt packs ≤40GB; the direct-S3 build route is CAS-safe per the nameservice protocol — RT1-verified); the build half is the gap (a first-principles bulk-ingest builder is required; hard-delete propagation unsolved; the 200M/550M-row facts exceed the pack door). Decisive scoping fact: sidecar rollup CUBES strictly dominate a full twin for the very family that motivated materialization (a twin still full-scans a 550M-row GROUP BY; a per-snapshot cube is O(1)) — materialize ANSWERS for rollups, reserve the twin for point-lookup/crawl/join/BI-serving families if they demand it after cubes.

**Strategic engine direction (RT1-corrected): delegate relational subplans to DataFusion with honest pricing** — Step-1 (TableProvider over our already-pruned scan lists + the coupled arrow 54→58/59 bump) is a de-risking beachhead only; the ceiling-busting value is Step-2 gate-widening, priced with its semantic surface (exact-BigDecimal-SUM vs Decimal128, 3VL, bag semantics — per-shape oracle re-bless). Co-primary and lower-risk: mechanical optimization of `materialize_batch`, the only lever reaching the graph-native residual that owns the remaining crawl-OOM class.

**Program hygiene needs a reset alongside the code:** the vbench perf gate is effectively blind (62% of members have no meaningful baseline — the floor; ALL blessed entries predate the optimization program), the resilience mechanisms (cancellation, memory budget, 429 backoff) have zero regression coverage, several mechanisms shipped without kill switches against house rules, and SWITCHES.md omits ~8 operator-relevant switches. The recommendations ladder (§6) sequences all of this: Tier-0 correctness (days) → Tier-1 harness trust (days) → Tier-2 admission/coverage wins (weeks) → Tier-3 strategic (quarters), with the implementation phase executing Tiers 0-2 as consolidated, locally-CI-reproduced draft PRs.

## 4. Materialization strategy (C3 + C4 facts; decision framing RT1-reviewed)

- **Serving side: solved today.** Native ledgers page on-demand from S3 (Range GETs; eager set = root + routing manifests; LeafletCache + DiskArtifactCache at the same /tmp root as parquet cache) — SF20-class twin (~147GB native) is Lambda-queryable; dataset size is NOT bounded by /tmp or memory. Solo consumes prebuilt fluree-pack-v1 (commits + index, no reindex) via streaming restore ≤40GB multipart (bplatz #626, live-validated 21GB/561M triples within the transactor window).
**Materialization builder — design stance:** the builder is designed from FIRST PRINCIPLES: bulk create-from/flpack-class ingestion (parallel commit generation + k-way-merge indexing), never transact-replay; snapshot-vector watermarks derived from Iceberg snapshot semantics directly. An earlier community PR (#1422) explored the same problem space; the design here does not derive from it — the technical comparison below records why its deployment shell does not fit this substrate.
- **Build side: the gap.** #1422 is an engine core (watermark protocol, append-only incremental snapshot windows, CDC latest-by-key dedup; 920 tests) whose deployment shell does not fit here: it runs an in-memory worker on a long-lived server node that solo does not run, is GCP-oriented, applies data through plain upsert rather than bulk import, and propagates deletes only via a CDC marker (hard/CoW deletes never retract). It is also 595 commits behind and conflicts with the current perf-line files. Solo structurally prevents Iceberg→native writes (virtual XOR native by construction) → twin-dataset + alias-repoint pattern, not in-place.
- **Arithmetic (measured anchors: 22.4 B/triple native; pack producer 1.06s/749MiB at sf01; 1.3M flakes/s build; #626 restore rate):** SF20 ≈ 7.0B triples → ~147GB native / ~157GB pack = 3.9× over the 40GB pack door; build ~90 min; restore ~3.1h = 12.6× one Lambda window. Facts ≤~120M rows fit the pack door; 200M/550M-row facts need direct-S3 build (uncapped; engine already supports S3+DynamoDB connections; assembly-only) or dedicated-transactor/resumable restore. **RT1-2 UPGRADE: the direct-S3-build route is receipted-SAFE, not inferred** — the DynamoDB nameservice publish protocol is CAS-guarded end-to-end (`attribute_not_exists(pk)` create, monotonic `#ct < :t` commit CAS, `#it < :t` index CAS, exact-CAS variants; storage-aws `mod.rs:671/1103/1229/1789/1966`), so out-of-band build + head-publish of a fresh twin is lost-update-safe; residual risks are the C3-named ones (hard-delete propagation, >40GB initial load, worker home), NOT concurrency. Caveat (RT1-6): db-layer repoint safety verified (`with_dataset` resolves once per query, `runner.rs:834`); SOLO-side alias-repoint atomicity unverified.
- **Sync: cheaper than expected.** The pack protocol is ALREADY incremental (want/have commit walk + index-root artifact set-diff, pack.rs:65-157) — store-to-store delta shipping exists unexposed. Iceberg-side increments via #1422's snapshot-window walk. Deletes remain the hard part (CDC marker only; hard-delete retraction requires removed-file row reads). PRECONDITION: F-AUD-2 fix (cut from main ≥ 7581f0ac8).
- **Decision framing:** materialization is a PER-TABLE/PER-FAMILY lever, not a binary — an unfiltered 550M-row GROUP BY is slow natively too; the rollup family's real cure is aggregate pushdown (virtual) or precomputed cubes (sidecar). [D1 options + ranking pending.]

## 5. Third-way strategy options (D1 delivered; ranking [FINAL-PASS] after RT1 + bench)

Eleven options enumerated in D1-strategy-options.md, each graded vs the residual timeout families / solo primitives / consistency / size / DataFusion relation: (1) snapshot×query-hash result cache; (2) shared warm tier (EFS or S3-Express read-through for catalog+footers+hot ranges); (3) acceleration sidecars — 3a per-snapshot stats/NDV, 3b pre-aggregated rollup cubes, 3c bloom/value-index, 3d denormalized wide-table; (4) scatter-gather MPP over Lambda fan-out; (5) per-source SQL pushdown (Snowflake-managed segment only); (6) adaptive per-table native-TWIN promotion (the (b)-spectrum; twin + alias repoint per C4's virtual-XOR-native constraint); (7) async/continuation protocol on durable-turn + job rows; (8) progressive/approximate with exactness labels; (9) writer-side layout advisory + implement the inert partition pruner; (10) partial/intermediate-result reuse.

Three load-bearing structural insights (D1): **(i) THE SNAPSHOT-KEYED CORRECTNESS LEMMA** — every acceleration artifact that is a pure function of an immutable snapshot-id (options 1, 2, 3a-d, 10) is EXACTLY-correct under the shipped per-query snapshot pin and adds ZERO staleness surface beyond the existing pointer-TTL; the sole correctness-expensive outlier is 6 (twin sync: sync-lag semantics + #1422 hard-delete ghosts + pre-#1508 resurrection). All artifact builds must gate on the V1 MoR-delete guard. **(ii) DOMINANCE** — sidecar cubes (3b) strictly dominate full native materialization for the ≥60M-row unfiltered-rollup family: a native twin still full-scans a 550M-row GROUP BY, a per-snapshot cube answers it O(1) — materialize the rollup ANSWER, not its input; full-twin materialization retains value for the point-lookup/crawl/join families and offline/BI-tool serving, not for rollups. **(iii) MULTIPLICATIVE COMPOSITION** — the levers hit different cost terms (DataFusion=execution, MPP=horizontal, warm-tier=fetch, cube/result-cache/partial-reuse=demand, async=envelope); DataFusion shrinks every other option's burden but never owns the extreme tail alone.
