READ(branch fluree-db-api/src/graph_source/r2rml_materialize.rs, module doc + fn body) — core API: `Fluree::materialize_r2rml_graph_source(source_graph_source_id, target_ledger_id, force_full) -> MaterializeResult {from_snapshot_id, to_snapshot_id, incremental, committed, rows_read, subjects_upserted, subjects_retracted}` in fluree-db-api (so it IS callable from a solo Lambda, unlike the server endpoints); per-(source,table) watermark persisted as a node `urn:fluree:materialize-state:{source}:{table}` IN the target ledger (injective `:`-escaping), read back automatically; `force_full` ignores it.

READ(branch, same file) — incremental model: each logical table reads against its own watermark; a `(from,to]` snapshot window is scanned incrementally (added data files only) when the window is append/compaction-only, else the live table is FULL re-read; a no-delta poll (`from == to`) commits nothing (`committed=false`, no commit churn); the enabling algorithms are new in this PR: `SendScanPlanner::plan_incremental` (added files by effective data sequence number with Iceberg null/0 seq inheritance), `TableMetadata::snapshot_window` / `window_is_append_only` (parent-chain ancestry walk, branch/expired detection) — NONE of these exist at the audit tip (MEASURED grep: no hits for plan_incremental/snapshot_window/window_is_append_only in fluree-db-iceberg at 10e073fe9).

READ(branch, same file + fluree-db-r2rml materialize/term.rs diff) — update semantics: "latest-by-key" mode activates when a DeleteConvention and/or an `order_by` column is configured; rows per subject are ranked by the order_by column (int/date/timestamp only, validated per batch via new `column_is_orderable`; absent/mis-typed columns fail loud) and the winner is applied as a WHOLE-SUBJECT REPLACE (every subject seen in the window retracted, then live winners re-asserted — clears dropped fields); with neither configured the pass is "legacy additive" per-predicate merge; latest-by-key requires ONE TriplesMap per logical table (multi-TM same-table configs are rejected loudly).

READ(branch, same file) — delete semantics, the load-bearing caveat: a row is retracted ONLY when the configured delete-marker column classifies it as a tombstone (CDC full-image soft-delete sinks); a subject that is HARD-deleted at the source (file rewritten without the row — the copy-on-write pattern) is never "seen in the window", so it is NEVER retracted, not even under force_full — there is no target-diff/purge step; the PR body's "removes a subject when its key disappears from the source" overstates this. Row-level delete files (v2 merge-on-read) are explicitly "future work" (commit 2fc2170 message). Net: against a Snowflake-managed COW table with real DML deletes, a #1422 twin accumulates ghost subjects indefinitely.

READ(branch :309-331) — apply path: `self.create_ledger(target)` if absent, then `self.upsert(ledger, JsonValue::Array(nodes))` — i.e. the NORMAL JSON-LD transact path (novelty → background indexer), NOT the bulk-import pipeline, NOT pack/restore; two ordered commits per changed refresh (retract-commit, then upsert+watermark-commit) so the watermark advances only if the upsert lands; a crash between them re-reads the same window (self-healing) but leaves a visible intermediate t where retracted subjects are absent (no snapshot isolation across the pair).

PR(1422 body) — worker + endpoints: `MaterializeTrackingWorker` (fluree-db-api/src/materialize_worker.rs) is a per-job (`TrackedJob{source,target,interval,next_due}`) ticker with default 30 s poll; state is IN-MEMORY PER NODE, lost on restart (jobs must be re-registered; watermark durability in the target ledger makes re-registration resume incrementally); endpoints POST /iceberg/{materialize,track,untrack} + GET /iceberg/tracking live in fluree-db-server (solo runs no fluree-db-server; RELAYED C4: solo embeds fluree-db-api in Lambdas); /track runs an immediate first sync.

PR(1422 body) — auth/deployment orientation: the fifth commit adds `google_metadata` refreshable catalog auth (GCE/GKE Workload Identity metadata server) so a long-running tracker against a Google (BigLake) REST catalog survives ~1 h token expiry; manual e2e was against a Google Iceberg REST catalog. ## 3. Native import machinery at the audit tip (the fast paths and why they're fast)

READ(fluree-db-cli/src/commands/create.rs:300-460) — `fluree create <ledger> --from <path>` dispatch: `.flpack` → restore (below); CSV/Cypher → converted to ND-JSON-LD → chunked bulk import; Turtle/JSON-LD file or directory → `fluree.create(ledger).import(path)` bulk pipeline; a stray `.ttl` reaching the transact branch is force-redirected to bulk import "to avoid novelty limits" (comment at :370) and `.jsonld` import "bypasses novelty" (comment at :921) — the pipeline's speed comes from skipping the transact/novelty machinery and building the binary index directly during ingest.

READ(create.rs:434-451) — bulk-import tuning surface: `parallelism`, `memory_budget_mb` (auto = RAM-tiered; the auto=80% figure previously OOM'd a machine — memory note), `chunk_size_mb`, `leaflet_rows` default 25,000, `leaflets_per_leaf` default 10 (i.e. ~250K rows per leaf target — matches the measured ~557 KB leaflet objects below); crash-breadcrumb JSON written ≤1/s for OOM/SIGSEGV forensics (create.rs:470-520).

MEASURED (prior internal import benchmark, same hardware) — LDBC SNB sf3 Turtle imported at ~1.30M flakes/s through this pipeline; native-sf01's provenance is this exact path: "emit_ttl.py -> enterprise-sf01.ttl.zst -> imported + indexed" (READ fluree-bench-virtual/targets/native-sf01.json), and the resulting ledger has exactly 1 commit (MEASURED via pack output) — a bulk import is one commit + a prebuilt index, which is why the pack/restore story below is so clean.

READ(fluree-db-api/src/pack.rs:52-57, lib.rs:4515; docs/cli/server-integration.md:230) — PRODUCER: `Fluree::archive_ledger` / `stream_pack` emits fluree-pack-v1: header + manifest frames (incl. a `phase:"nameservice"` manifest so the importer reconstructs head pointers) + one data frame per CAS object (commit blobs, txn blobs, dict packs, index leaves) + end frame; CLI = `fluree export <ledger> --format ledger -o file.flpack` (all commits + txn blobs + binary index artifacts unless --no-indexes); it packs FROM a live ledger via the normal handle.

MEASURED — producer cost on native-sf01 (35,238,778 triples, 751 MiB store): 1.06 s wall / 0.11 s user / 0.32 s sys, output 785,645,198 B (749 MiB), "1 commits, 0 txn blobs, 676 index artifacts", peak RSS 732 MB (≈ the largest dict-pack frame, not ledger size — frames buffer one whole CAS object; dict packs target 256 MiB, READ commit_transfer.rs:56-63). Local NVMe→NVMe, i.e. I/O-bound streaming at ~740 MB/s; from S3 the producer is bounded by object-store read throughput, not CPU (3.55B instructions retired total ≈ 0.5 s of CPU).

READ(pack.rs:65-157) — the pack protocol is INCREMENTAL-CAPABLE: a want/have commit walk (BFS from `want` head CIDs stopping at `have` CIDs — git-fetch-shaped, :65-88) AND an index-artifact set-diff ("collect all CAS artifact CIDs reachable from the want index root … then subtract the have root's reachable set", :134-157) — structural sharing means a t2 index re-uses most t1 leaflets, so a store-to-store sync ships only new commits + new/changed leaflets; this is the clone/pull replication path (READ docs/cli/server-integration.md:8: "clone / pull / fetch (content-addressed replication by CID, via pack + storage proxy)"). Plus commit-level transfer APIs `export_commit_range` / `import_commits_bulk` / `import_commits_incremental` / `push_commits`+`prepare_push` (READ commit_transfer.rs:270,305,1271,1435,1966).

READ(commit_transfer.rs:56-92,113-121,1597-1700) — RESTORE (why it's fast): `restore_ledger` = create empty target → `restore_into_created`: sequential frame decode (CPU-cheap), SHA-256 verify every frame against its CID (commit-v2 blobs over their canonical sub-range), then CAS writes dispatched into a bounded pool — RESTORE_MAX_WRITES_IN_FLIGHT=32 concurrent, RESTORE_MAX_BYTES_IN_FLIGHT=512 MiB, RESTORE_MAX_FRAME_PAYLOAD=1 GiB sanity cap (sized 4× above the 256 MiB dict-pack target after the frame-cap bug) — the comment is explicit that serial per-object S3 round-trips "blow a serverless time budget", hence the overlap; finish = set commit head t + index head t; failure = soft-drop rollback (nameservice retract; orphan CAS blobs are harmless/idempotent). NO transaction replay, NO revalidation beyond hashes, NO reindex — a restore is a verified CAS copy plus two head pointers, which directly answers the offline-builder question: YES, an offline builder can emit commits+index (bulk import → archive_ledger) and the serving side restores it as-is; requires a "managed storage backend" (READ commit_transfer.rs:1675).

READ(docs/cli/server-integration.md:1599-1766; fluree-db-server/src/routes/import.rs:38,170,192-227; import_jobs.rs:16) — SERVER FRONT DOORS: direct `POST /import/*ledger` streaming body; for size-capped gateways (explicitly "e.g. an app on AWS Lambda behind API Gateway, ~6–10 MB caps") the negotiated flow: discovery `/.well-known/fluree.json` `import:{modes:[direct|presigned-put|multipart-put], direct_max_bytes}` → `POST /import-upload` mint (multipart plan when size ≥ threshold; MAX_MULTIPART_PARTS=10,000) → token-in-URL blob/part PUTs (possession-authorized, presigned-style) → `POST …/complete` starts `restore_ledger` ASYNCHRONOUSLY ("can outlast a single request (and your function timeout)") → `GET …/{id}` poll {awaiting-upload,running,succeeded,failed}; mint/complete/status admin-protected; reference backend gated by `import_presign_enabled` (env FLUREE_IMPORT_PRESIGN_ENABLED); in-memory job registry, IMPORT_JOB_TTL=3600 s.

RELAYED(C4, VERIFIED there) — solo's consumer half of this: router mints presigned/multipart uploads (256 MiB parts, multipart above 5 GB), MAX_FLPACK_IMPORT_SIZE = 40 GB, the transact Lambda runs `process_begin_import` streaming S3→`FlureeClient::restore_ledger` (fluree-lambda-transact/src/import.rs:243,385) with NO /tmp spool and NO reindex; resume = SQS redelivery + ledger-state guard (t>0 ⇒ don't re-restore); bplatz authored this flpack layer in solo #626 (merged 2026-06-17) on Parsell's #498 begin-import foundation; #626's live validation: a 21 GB / 561M-triple archive restored "within the transactor window" (PR https://github.com/fluree/solo/pull/626 body).

READ(fluree-db-connection/src/lib.rs:156-158,221,283-333; fluree-db-storage-aws/Cargo.toml:10-12 + src/dynamodb/{mod,schema}.rs) — STORAGE BACKENDS: the connection layer takes JSON-LD config with `StorageType::S3` ({"@id":"s3Storage","@type":"Storage","s3Bucket":…}, separate commit/index storage bindings) and fluree-db-storage-aws ships default features ["s3","dynamodb"] including a DynamoDB module — S3 CAS + DynamoDB nameservice live in db proper (RELAYED idx-paging concurs), and solo's transact/indexing/query Lambdas already run fluree-db-api against exactly this. INFERRED (direct-S3 build): nothing packaged points the BULK IMPORT pipeline at an S3 connection today (the CLI builds against a local home; its S3 involvement is read-side vended-credential direct reads, READ fluree-db-cli/src/context.rs:348-416), but the import pipeline writes through the same storage trait, so "builder on EC2/ECS/laptop with S3+DynamoDB connection config → import → head publish" bypasses BOTH the 40 GB pack cap and the restore step with zero engine changes — an assembly+credentials job. The near-equivalent that exists today with no new wiring: build locally, `fluree export --format ledger`, restore through solo's negotiated door (capped 40 GB) or through fluree-db-server's (uncapped by solo's constant).

PR(https://github.com/fluree/db/pull/1518) — also in flight (OPEN, MERGEABLE, updated 2026-07-18): extends the negotiated `/import-upload` handshake to accept RAW SOURCE data (TTL/NT/NQ/TriG/JSON-LD/JSONL±gz/zst, CSV, Cypher dumps) converted server-side via shared `fluree_db_api::import_source` helpers — i.e. a remote door straight into the fast bulk-import pipeline, dropping the customer's sidecar. Refused on Raft-replicated servers.

RELAYED(idx-paging agent; item declared CLOSED by coordinator) — QUERY-SIDE PAGING (the pivotal feasibility fact): native-ledger query evaluation pages index nodes on demand from S3 via Range GETs; the eager set at ledger open is the index ROOT + routing manifests only (commit head + ns record + root, not leaves, not dicts wholesale); caching tiers = in-memory LeafletCache + DiskArtifactCache at /tmp/fluree_binary_cache (the SAME disk-cache root the Lambda already uses for parquet footers/row-groups), with mmap, promotion and prewarm behavior; therefore a native twin of ANY size is queryable from a 10 GB-/tmp Lambda — cold cost scales with leaflets TOUCHED by the query (avg leaflet object ≈ 557 KB, MEASURED §5), not with ledger size. ## 4. Correctness: the resurrection/duplicate bug family, and #1518's reindex fixes

Memory baseline (pre-audit): v4.1.2 data-integrity bug — a value asserted AND retracted in the same un-indexed window is RESURRECTED by `fluree index`; minimal repro verified 2026-07; never filed as its own issue.

PR(https://github.com/fluree/db/issues/1412) — the filed sibling: aaj3f, 2026-07-01, from Solo QA (Laurent Bégin, Radio-Canada KG05), Critical: re-inserting existing triples yields DUPLICATE rows (~16× observed) + assert/assert/retract history churn; live-novelty queries correct, corruption appears only after an incremental index build and compounds per build; full rebuild silently heals.

PR(https://github.com/fluree/db/pull/1508) — the fix, MERGED TO MAIN 2026-07-18T13:43Z (main tip 7581f0ac8): (1) `dedup_fact_lifecycles` in `resolve_incremental_commits_v6` — set-semantics lifecycle collapse on resolved V2 fact identity, re-assert of asserted fact = no-op, same-t ties retract-wins, mirroring NoveltyFactState/overlay/KWayMerge exactly; (2) base-presence-aware stats deltas (fixes permanent per-property count inflation on every re-assert); (3) history sidecar: no retract entry for a fact the leaf never materialized — the PR names the exact ghost: "a fact asserted and retracted within one window deduped to a bare retract" would make time-travel replay "fabricate the fact's presence at every t before the retraction", and the rebuild path now skips retract-winner lifecycles with no assert anywhere in the commit log. INFERRED (strong): this is the resurrection mechanism from the memory repro; #1508 closes it for both incremental and rebuild paths — not re-verified against the exact repro this session.

PR(1508 body, residuals) — knowingly left open: a fact asserted+retracted within one indexing window is invisible to INDEX-SERVED time travel during its brief lived interval (novelty still serves it until indexed); full-rebuild resolves re-asserts to highest-t assert while incremental keeps first-assert t (t-provenance divergence, parked as a blocking design decision in history-transition-log-plan.md); ALREADY-published duplicate rows / corrupt stats / stale bare-retract history persist until a full reindex — the fix stops new damage only.

MEASURED (git) — deployment status of the fix: NOT in v4.1.2 (tag b8dedb244, 2026-07-10); NOT in the audit tip 10e073fe9 (merge-base with origin/main = a49ac3fc2, the #1450 merge); NOT in solo #788's engine pin bca124e4d (#1514 tip, pinned before 2026-07-18); therefore EVERY currently-deployed and currently-pinned engine carries the family. Materialize-and-sync relevance is direct and severe: latest-by-key full-refresh and legacy-additive re-syncs RE-ASSERT unchanged facts by design — on any pre-#1508 engine that is precisely the trigger that multiplies index rows per sync cycle and inflates stats; and a sync stream is a continuous assert/retract source for the in-window ghost. Fact: a materialization engine must be cut from main ≥ 7581f0ac8, and any twin built before it needs a one-time full reindex after upgrade.

PR(https://github.com/fluree/db/pull/1518) — "reindex OOM" relevance, precisely: the headline OOM fix is QUERY-side (Cypher UNWIND reified-edge probe, 35 s/OOM → 1.1 s flat-memory via batched annotation OPTIONAL probes) — it does NOT change the memory profile of reindexing a large ledger inside a Lambda; what IS sync-relevant in it: (a) `Fluree::reindex` raced a background indexer publish and could rebuild from a stale NsRecord — now cancels, waits idle, re-fetches (a correctness prerequisite for any "repair by reindex" step in a sync pipeline); (b) annotation-arena sealing fixes for write-only ingest (transient backend load; arena preserved across full rebuild under Augment coverage) — relevant iff a twin carries reified/annotation data. State OPEN/MERGEABLE (2026-07-18), base main.

## 6. Freshness / consistency model of a synced twin

READ(#1422 branch r2rml_materialize.rs) — t semantics under #1422: t advances per SYNC BATCH, not per source transaction — two commits per changed refresh (retract, then upsert+watermark), zero commits on idle polls; the watermark node (source, table, last snapshot_id) is ordinary queryable data in the target ledger, so commit-t ↔ Iceberg-snapshot-id correlation is reconstructible from ledger history; time-travel on the twin resolves to sync-batch boundaries and maps 1:1 to Iceberg snapshots ONLY when the poll interval outruns the snapshot cadence (a batch spanning n snapshots collapses them into one t — intermediate snapshots are unrepresentable); the retract→upsert gap is a real visible intermediate state at t_retract (no cross-commit isolation).

READ(#1508 body, residual) + INFERRED — post-#1508, a twin additionally loses index-served time-travel visibility of any fact whose entire lifetime fits inside one indexing window; for BI-style sync freshness this is benign, for audit-trail claims it is not — worth stating in any "time travel over your warehouse" pitch.

RELAYED(C4) — solo surfacing today: datasets are native ledgers; catalogs/mappings/datasets rows live in the per-stack `_system` ledger; virtual datasets carry Sourcing::Iceberg{tableRef}; virtual and native are disjoint and there is no lastSync/freshness field for a materialized-from-Iceberg concept because the concept doesn't exist in solo yet — freshness surfacing is greenfield UI/contract work, with the job-row + status-table pattern (RECORD_TYPE_MATERIALIZATION rows, C4) as the obvious substrate.
