## 0. Bottom line up front

The IO- and pruning-layer techniques Fluree HAS (projection, range coalescing, row-group min/max pruning, record_count COUNT(*), scan top-k, footer/scan-file caching) are **standard and correctly built** — none is idiosyncratic. The techniques Fluree is MISSING (page-index/offset-index pruning, bloom filters, dictionary pruning, late materialization, partition pruning, manifest-summary pruning, async prefetch, merge-on-read deletes) are **all standard and all absent**, and several are one feature-flag or one builder-method away in crates already linked. The aggregate-pushdown work (`fused_aggregate.rs`) is **sound per-slice but architecturally idiosyncratic**: it is a hand-rolled, pattern-matched reimplementation of a columnar analytical engine's hash-aggregate + pushdown, gated per-shape, with a growing decline chain (the 5-gate OOM query, `star_constraints` over-count holes, mixed-key/interior-fact extensions, no spill). The measured 56k-rows/s/core ceiling that governs the whole deployed problem is **not** Parquet decode — it is per-row RDF term materialization, a cost no analytical engine pays. The renegotiation answer is a qualified **yes**: incrementally delegate the *relational* subplan (scan+filter+join+group-by) to an embedded, in-process, Rust, arrow-native engine (Apache DataFusion), constructing RDF terms only on the small final result, while keeping the hand-rolled path for the genuinely graph-shaped residual. This is a migration behind the admission gate that already exists, not a rewrite, and it inverts the cost model from "materialize every input row" to "materialize every output row."

## 1. Technique-level SOTA — how mature engines execute a cold Iceberg/Parquet-on-S3 scan

The mature open-source reference is the layered Parquet pruning stack, most crisply documented by DataFusion, and matched (with variations) by DuckDB, Trino/Presto, ClickHouse, Athena, and Snowflake. The stack applies filters as a cascade of progressively finer skips **before** decoding row values, in this order: projection pruning (read only referenced columns' byte ranges) → row-group min/max stats pruning → bloom-filter pruning (equality predicates the min/max can't cut) → page-level stats pruning via the column index / offset index (skip individual data pages inside a surviving row group, building a `RowSelection`) → row-level filter pushdown with late materialization (decode filter columns first, evaluate the predicate, then decode the remaining projected columns only for surviving rows). WEB(https://datafusion.apache.org/blog/2025/03/20/parquet-pruning/) WEB(https://datafusion.apache.org/blog/2025/03/21/parquet-pushdown/)

DataFusion is now the fastest single-node engine for querying Parquet (ClickBench), and its `ParquetExec` carries "every optimization for reading Parquet, including projection pushdown, predicate pushdown (row group metadata, page index, and bloom filters), limit pushdown, parallel reading, interleaved I/O, and late materialized filtering." WEB(https://datafusion.apache.org/blog/2024/11/18/datafusion-fastest-single-node-parquet-clickbench/) The "interleaved I/O" is the async prefetch pipeline: the arrow-rs `ParquetRecordBatchStream` / `ParquetObjectReader` requests multiple byte ranges simultaneously, coalesces adjacent ranges, and fetches ranges in parallel while decoding, so fetch and decode overlap rather than serialize. WEB(https://arrow.apache.org/rust/parquet/arrow/async_reader/store/struct.ParquetObjectReader.html) WEB(https://arrow.apache.org/blog/2022/12/26/querying-parquet-with-millisecond-latency/)

DuckDB's Parquet reader implements the same shape from a different codebase: aggressive column-projection pushdown via `ColumnReader`, page reading + prefetching + range coalescing coordinated per column, the page index to rule out whole data pages, and (added March 2025) Parquet bloom-filter read/write. WEB(https://duckdb.org/2025/03/07/parquet-bloom-filters-in-duckdb) A recent survey notes the split in practice: "Arrow and DuckDB only adopt zone maps at the row group level for Parquet, while InfluxDB and Spark enable PageIndex and Bloom Filters for better selection performance" — i.e. page-index/bloom are the current frontier, not universal, but every serious engine has at least the row-group + projection + coalescing base. WEB(https://arxiv.org/pdf/2304.05028)

The critical throughput fact for this audit: Parquet→Arrow decode is vectorized and fast — GB/s per core, dictionary-preserving reads up to 60× faster than naive, millions of rows/s/core for typical columns. WEB(https://arrow.apache.org/blog/2022/12/26/querying-parquet-with-millisecond-latency/) WEB(https://ursalabs.org/blog/2021-r-benchmarks-part-1/) An aggregate (`SUM(x) GROUP BY k`) over decoded Arrow runs as a vectorized hash aggregation over columns — no per-row object is ever constructed. This is the yardstick the deployed 56k-rows/s/core measurement (A-doc §3) must be held against: 56k rows/s is ~2 orders of magnitude below vectorized decode, which means the deployed bottleneck is **not** the Parquet layer at all. INFERRED

On the Iceberg spec side, mature engines exploit features Fluree does not touch: hidden partitioning + partition-spec transforms (identity/bucket/truncate/year/month/day/hour) so a filter on a real column prunes whole partitions the writer derived at write time; per-manifest partition-field summaries (lower/upper/contains-null) to skip entire manifest files before reading them; Puffin statistics files whose one standardized blob is an NDV Theta sketch (apache-datasketches-theta-v1) for cardinality-driven planning and file skipping; merge-on-read positional + equality delete files that a correct reader MUST apply to avoid returning deleted rows; and metadata tables ($files/$manifests/$partitions/$snapshots/$history) for zero-scan introspection. WEB(https://iceberg.apache.org/spec/) WEB(https://lakeops.dev/blog/iceberg-puffin-statistics-guide) WEB(https://dev.to/alexmercedcoder/hidden-partitioning-how-iceberg-eliminates-accidental-full-table-scans-2pd5)

## 2. Architecture-level SOTA — the four families the baseline could renegotiate toward

**(2a) OBDA / R2RML query rewriting (Ontop) — the native direction of the R2RML spec.** Ontop answers SPARQL over relational data by translating SPARQL→SQL through the R2RML mapping and delegating execution to a SQL engine, deliberately avoiding triple materialization. Its optimizations are exactly the ones a hand-rolled per-pattern fold has to re-derive: self-join elimination (multiple triples over one table collapse to one scan), semantic query optimization using DB constraints (functional dependencies / keys eliminate joins), foreign-key-driven redundancy removal, and pushing joins/aggregations/filters into the SQL engine rather than folding them in-memory. WEB(https://www.semantic-web-journal.net/system/files/swj1278.pdf) The reported result: Ontop's SQL "is superior to that of well known systems that rely on SQL to execute SPARQL, and superior to that of well-known triple stores." WEB(https://www.semantic-web-journal.net/system/files/swj1278.pdf) The correctness surface of the rewriting approach is well-studied and bounded: SQL NULLs vs RDF absent-value/blank-node semantics, SPARQL bag/duplicate semantics, and datatype-correct RDF term construction from SQL values. WEB(https://www.semantic-web-journal.net/system/files/swj1278.pdf) This is the standard architecture for *exactly Fluree's problem* (R2RML virtual graphs over relational/columnar sources); Fluree's hand-rolled scan+operator fold per pattern is the road-less-traveled alternative.

**(2b) Embedded analytical engine inside Lambda.** DuckDB-in-Lambda is a proven pattern (BoilingData: managed distributed DuckDB on Lambda, ~206 ms average warm response over 1,146 calls, S3 read via httpfs, DuckDB file treated as immutable read-only artifact). WEB(https://boilingdata.medium.com/lightning-fast-aggregations-by-distributing-duckdb-across-aws-lambda-functions-e4775931ab04) WEB(https://www.boilingdata.com/duckdb-lambda.html) The Rust-native equivalent is DataFusion: same language as Fluree, arrow-native, Apache-2.0, in-process (no FFI), and it carries the entire Parquet pruning + pushdown + late-materialization + vectorized-aggregate + spill stack that §1 enumerates and §3 finds missing. Rust on Lambda has the lowest cold-start class of any runtime (init 12–28 ms; app binaries 5–10 MB before the engine), and AWS added first-class Rust support in late 2025 — so an embedded Rust engine adds no new runtime and no FFI boundary, only link size. WEB(https://maxday.github.io/lambda-perf/) WEB(https://www.nandann.com/blog/rust-aws-lambda-production-guide) Decisive detail for Fluree specifically: the crate already links `arrow = "54"` + `parquet = "54"` (fluree-db-iceberg/Cargo.toml; workspace `Cargo.toml:178`), the exact substrate DataFusion is built on, so "adopt DataFusion" is version-tracking + lowering work, not a new dependency universe. READ(fluree-db-iceberg/Cargo.toml) READ(Cargo.toml:178)

**(2c) Serverless MPP (scatter-gather over many Lambdas).** Starling (SIGMOD 2020) runs a scalable query engine on cloud functions, shuffling intermediate results through S3 with straggler mitigation ("doublewrite"), achieving interactive latency at lower cost than provisioned systems when queries arrive ≥1 minute apart, on 1 TB TPC-H. WEB(https://pages.cs.wisc.edu/~yxy/cs839-s20/papers/starling.pdf) Lambada is the cold-data analytics analog. WEB(https://www.researchgate.net/publication/341747852_Lambada_Interactive_Data_Analytics_on_Cold_Data_Using_Serverless_Cloud_Infrastructure) Applicability to Fluree: the 36–200 M-row FACT scans that are categorically hopeless on one 6-vCPU Lambda within 55 s (A-doc Appendix A.2) become tractable if fanned across N Lambdas each scanning a file subset, with a partial-aggregate gather — this is the horizontal-scale answer to "6 cores is the hard ceiling." It is heavy (orchestration, straggler handling, S3-shuffle cost) and solo-owned, so it is a strategic option, not a near-term lever. INFERRED

**(2d) Pushdown-to-source (issue SQL to Snowflake).** The deployed data is Snowflake-managed Iceberg with Snowflake's Polaris REST catalog, so the Trino Snowflake-connector precedent applies: push predicate/projection/aggregate/join down, and for the extreme case use "full query passthrough" to delegate an entire query to the source and receive a small result. WEB(https://trino.io/docs/current/connector/snowflake.html) WEB(https://www.starburst.io/blog/introducing-full-query-passthrough-for-faster-query-federation/) But this option is **source-type-bounded**: it works only for the Snowflake-managed source, and is DOA for the BYO-IAM customer S3 buckets, which are raw Parquet + a REST catalog with **no compute engine behind them** — there is nothing to push SQL to. It also re-introduces a Snowflake warehouse dependency, spin-up latency, per-query warehouse cost, and undercuts the "query your data in place without standing up a warehouse" value proposition. So it is a per-source optimization, not an architecture. INFERRED

**(2e) Caching tiers.** S3 Express One Zone gives single-digit-ms latency and ~9 GB/s vs S3 Standard's ~1 GB/s, and AWS documents it as a caching layer in front of S3 Standard — directly applicable to the cross-region cold-parquet tail (A-doc §A.5(i)). WEB(https://aws.amazon.com/blogs/storage/using-amazon-s3-express-one-zone-as-a-caching-layer-for-s3-standard/) EFS-for-Lambda gives a shared, persistent filesystem across containers, which is the architecture-level answer to the per-container ephemeral `/tmp` that is cold on every one of the 16 cold containers a conversation touched (A-doc §2a, cross-track reconciliation). Snapshot-id-keyed result caching is the highest-leverage cache for THIS workload: an Iceberg snapshot-id is immutable, so a grouped-aggregate result keyed by (snapshot-id, query-hash) can be cached indefinitely — which directly kills the "agent fires ~39 whole-table rollups in one turn" demand pattern (the strategy slate §exec-summary), turning the second identical rollup into a metadata lookup. INFERRED

### 3d. The receipt that reframes everything — where the 56k rows/s actually goes

The measured ceiling is `wall ≈ rows_materialized / (56k × cores)` (the strategy slate §exec-summary), and the code inventory pinpoints the loop: `materialize_batch` iterates every row (`for table_row_idx in 0..num_rows` READ(fluree-db-query/src/r2rml/operator.rs:2176)) and for each row iterates **all** predicate-object-maps building every term (READ(fluree-db-query/src/r2rml/operator.rs:2380)), where each cell does a HashMap name→index lookup **per cell** (READ(fluree-db-r2rml/src/materialize/term.rs:496) → `index_by_name` READ(fluree-db-tabular/src/batch.rs:88)) plus a `String` allocation per cell (READ(fluree-db-r2rml/src/materialize/term.rs:506)), and each templated IRI runs a regex `captures_iter` per row plus a per-char `iri_escape` with `format!("%{:02X}")` per non-safe byte plus multiple `String::replace` allocations (READ(fluree-db-r2rml/src/materialize/term.rs:648-682,168-199)). This is per-row, per-cell, allocation-heavy RDF term construction — the exact work a columnar aggregate skips entirely, and ~2 orders of magnitude below vectorized decode. INFERRED The strategy-slate's own T2.2 ("56k rows/s for 4 columns is slow — profile it") is pointing at this loop; the SOTA framing is sharper: it is not a loop to shave 2× off, it is a cost class an analytical engine does not have.

## 4. The central strategic finding — the fused-aggregate program is a hand-rolled columnar engine

Read as a set, the shipped and in-flight aggregate work (`fused_aggregate.rs` single-table fold; E1 shared-predicate class-fusion #1514; E2 join+flag; W4-2 mixed fact+dim group keys; W4-1/W4-1b const-object crawl folding; W4-3 VALUES lowering; the parked semi-join; the R3-A/B checkpoint+budget guard) is Fluree **re-deriving, one SPARQL shape at a time, the operator set a columnar SQL engine ships generically**: hash aggregation, projection/predicate pushdown, semi-join reduction, limit forwarding, and memory guarding. Each slice is individually sound and adversarially reviewed. But the program has three structural properties that the SOTA architectures do not: (1) an **admission gate per shape** — every new SPARQL pattern is a new `detect`/`resolve` case with its own decline conditions (the canonical OOM query declines for FIVE orthogonal reasons `the round-3 engine analysis` §1); (2) a **soundness tail that grows with coverage** — widening admission repeatedly surfaces silent-wrong-answer risks (the `star_constraints` over-count that ships only because the shape currently declines, the D-c5 adversarial pass O1; the folded-wildcard `has_star_members` mis-route caught in W4-1b's second pass); and (3) a **capability ceiling** — spill, cross-table expression aggregates, interior-fact streaming, and general join reordering are "large multi-part extensions, not slices" (`the round-3 engine analysis` §R1′), i.e. the hand-rolled path structurally cannot reach the shapes a general engine handles by default. The F-fix long tail (F14–F22, the W-waves, the E-series) is the empirical signature of this: it is not a run of bugs, it is the unbounded cost of hand-rolling an optimizer. INFERRED

The counter-fact that keeps this from being a slam-dunk "replace it": the RDF/graph residual is real and does NOT lower to relational algebra — property paths, `?s ?p ?o` wildcard crawls, blank-node cross-products, variable predicates, and reasoning are graph-native and must stay in the hand-rolled path. So the honest framing is not "replace the fold with an engine" but "**delegate the relational subplan; keep the graph core**." INFERRED

## 5. Verdict

### (a) Are the implemented strategies sound/standard, or idiosyncratic?

Sound and standard at the IO/pruning layer (projection, coalescing, row-group min/max, record_count, top-k, caching) — nothing there is weird or wrong, it is a correct subset of the mature stack. Idiosyncratic at the execution-model layer: row-at-a-time RDF materialization as the universal path (the 56k ceiling), and a per-shape hand-rolled aggregate optimizer with a growing admission/decline/soundness surface. The strategy slate itself is *well-reasoned within its frame* — the ranking (cheap correctness wins first, aggregate pushdown as the weeks-item, cache/region as secondary constants) is correct given the decision to keep the hand-rolled core. What the slate does not ask is whether the core should be kept, which is the renegotiation question below.

### (b) Top-5 missing generic techniques, ranked by expected impact for THIS workload

1. **Vectorized columnar aggregation (the general form of `fused_aggregate`).** Removes the 56k-rows/s materialization term for families A/B/C — the dominant deployed killers (36–200 M-row FACT rollups, 107–590 s → seconds). This is what DataFusion does generically; Fluree hand-rolls it per shape. Highest impact, and the strategic center of gravity.
2. **Semi-join reduction + spill-capable join/aggregation.** The 2-FACT OOM join (120 M ⋈ 36 M) and the sub-180 s OOMs need input reduction a cost-based optimizer derives, and completion the current typed-abort guard cannot give. A general engine has grace-hash-join + external sort. High impact on the join/OOM family.
3. **Async prefetch pipeline + arrow-rs async `ParquetObjectReader` (auto coalesce+prefetch).** Overlap fetch with decode and parallelize coalesced range GETs — one feature-flag + one reader swap, in a crate already linked. Attacks the sweep-bound cold-container tail and cross-region latency (q029/q031/q056). High impact on the fetch-bound classes, low effort.
4. **Iceberg partition pruning (hidden partitioning / manifest-summary skipping).** Currently a no-op stub. Zero benefit on the unpartitioned test data, but **high impact on real BYO customer tables** that use Iceberg partitioning — the difference between one partition and a full scan. The largest "standard Iceberg feature entirely absent."
5. **Persistent/shared cache tier + snapshot-id result caching.** EFS/S3-Express catalog+data cache across cold containers (kills the per-container cold catalog), and snapshot-id-keyed result caching (kills the ~39-rollup repeat-demand pattern). Addresses the catalog-latency class and demand reduction. Medium-high, architecture-shaped.

(Honorable mention, correctness not perf: **merge-on-read delete handling** — MISSING/IGNORED, a silent-wrong-answer risk for BYO merge-on-read tables that must be gated or implemented before that segment onboards such writers.)

### (c) The renegotiation — keep hand-rolled fold vs delegate to an embedded engine vs push SQL to Snowflake

**Recommendation: incrementally delegate the relational subplan to Apache DataFusion (in-process, Rust, arrow-native, already-linked arrow/parquet, Apache-2.0), constructing RDF terms only on the small final result; keep the hand-rolled path for the graph-native residual. Do NOT rewrite; do NOT make Snowflake-pushdown the architecture.**

Why not "keep hand-rolled": lowest disruption, but you keep paying the unbounded F-fix long tail (every new shape = new admission gate + decline audit + soundness review), you never escape the 56k/s ceiling for any non-fused shape, and the soundness surface grows with coverage (§4). This is a correct choice only if the workload never widens beyond the shapes already fused — which the deployed agent-driven traffic (39 varied rollups per turn) directly contradicts.

Why not "push SQL to Snowflake as the architecture": source-type-bounded (works for Snowflake-managed Iceberg, DOA for BYO raw-parquet with no engine — §2d), re-introduces warehouse cost/latency/dependency, and undercuts the in-place value prop. Keep it as a **per-source fast path** for the Snowflake-managed segment (a real optimization when the source IS a warehouse), not the general answer.

Why DataFusion, concretely: the R2RML rewrite already produces a relational-ish plan (star scans, FK joins, group-bys); instead of folding it row-by-row into RDF and re-aggregating, lower that relational subplan to a DataFusion logical plan over an Iceberg `TableProvider` and execute vectorized — inheriting page-index/bloom/late-materialization/partition-pruning/hash-aggregate/semi-join/spill **maintained upstream**, and inverting the cost model from "materialize every input row" to "materialize every output row." Same language (no FFI, unlike DuckDB), same runtime and cold-start class (Rust), same arrow/parquet 54 substrate already linked (READ(Cargo.toml:178)), clean license (Apache-2.0 vs DuckDB's MIT-core + C++ FFI + extension licensing). Maintenance: you inherit upstream's pruning/deletes/partition maintenance and delete the hand-rolled optimizer, at the cost of tracking DataFusion↔arrow version pins (DataFusion pins specific arrow versions; Fluree already sits on arrow/parquet 54, so this is version discipline, not a port). Lambda constraints: no new runtime, no FFI, same cold-start class; DataFusion's spill directly fixes the OOM class the checkpoint guard can only convert to a typed abort. Latency floors: for the aggregate family the floor drops to vectorized decode (GB/s) + hash aggregate — seconds on the same 6 vCPU — but the fetch-bound cold-container tail (catalog latency, ~69k-file fan-out, cross-region) still needs the cache/region/prefetch/partition levers **regardless of engine**, so this recommendation is necessary-not-sufficient and must ship alongside the §5(b)#3–#5 IO/cache work. Where NOT to delegate: the graph-native residual stays hand-rolled — this is delegate-the-relational-subplan, keep-the-graph-core, not a wholesale replacement.
